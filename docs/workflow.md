# Workflow

## 시작

요청 목적과 완료 조건을 파악하고 현재 브랜치, 작업 트리, 관련 코드와 문서를 확인한다. 기존 변경을 덮어쓰거나 되돌리지 않는다. 작업 범위에 영향을 주는 불확실성은 확인하고 독립적으로 진행할 수 있는 일은 계속한다.

모든 변경은 feature branch에서 수행한다. 브랜치는 기본적으로 `codex/` 접두사를 사용하고, commit 메시지는 `feat:`, `fix:`, `chore:`, `docs:` 등의 conventional commit 형식을 따른다. `main`과 `master`에는 force-push하지 않는다. PR을 작성하는 경우 제목과 설명은 한국어로 작성한다.

## 필요한 계획 선택

| 상황 | 필요한 기록 |
| --- | --- |
| 오타, 명확한 작은 수정 | 바로 구현하고 검증 |
| 여러 세션, 여러 모듈, 계약·저장 구조·운영 영향 | [ExecPlan](exec-plans/index.md) |
| 제품 행동이나 정책이 불명확함 | 기존 요구사항 문서 정리, 필요하면 Product Spec |
| 상태, 외부 호출, 대안과 실패 경계 검토가 필요함 | 필요하면 Design Doc |
| 장기간 유지할 중요한 기술 선택 | 필요하면 Decision 기록 |

모든 변경마다 모든 문서를 만들지 않는다. 파일 수만으로 문서 분량을 늘리지 않고 위험과 작업 중단 가능성을 기준으로 판단한다.

## 구현과 권한

작업에 필요한 변경을 작게 수행한다. 관련 계약과 문서를 함께 갱신한다. 실행 계획이 있으면 진행, 발견과 결정을 계속 기록한다.

새 production dependency 추가와 비밀 설정 파일의 생성·변경은 사용자의 승인을 받는다. 이미 해당 작업에 승인받았다면 같은 내용을 다시 묻지 않는다. 되돌리기 어려운 데이터 변경과 배포·발행·외부 전송은 현재 요청이 해당 행위를 승인하는지 확인하고, 승인 범위 밖이면 구체적인 변경안과 영향을 준비한 뒤 확인받는다. 명확히 승인된 일반 변경은 계속 진행한다.

이전의 migration이나 공개 계약을 변경할 때는 기존 사용자·데이터와의 호환성을 검토한다. 필요한 변경 순서, backfill, 실패 시 복구 방법과 확인할 환경을 계획에 적는다.

## 검증

명령과 환경의 기준은 [Development](development.md)다.

- source 변경 뒤에는 관련 테스트를 실행한다. 필요한 정적 분석, 포맷, 타입 검사와 빌드를 수행한다.
- 새 동작과 회귀 위험에 맞는 테스트를 사용한다. 구현을 그대로 복제하는 테스트를 늘리지 않는다.
- 저장 구조, 권한, 외부 연동과 비동기 상태 변경은 해당 경계의 실패·중복·재시도·동시성도 검증한다.
- 문서만 변경하면 코드 테스트는 생략할 수 있다. 링크, 경로, 명령 설명, 자리표시자와 문서 일관성을 확인한다.
- 통과한 검증은 변경이나 새로운 우려가 생길 때 다시 실행한다. 필수 검증을 못 했으면 이유와 남은 영향을 기록한다.
- Git 저장소에서는 완료 전에 `git diff --check`로 공백 오류를 확인한다.

실행 명령, 결과, 실행 환경과 미실행 범위를 남긴다. 로컬 테스트, CI, 배포, 실제 외부 시스템에서의 결과를 각각 구분한다. 코드나 빌드만 확인하고 운영 동작까지 검증했다고 표현하지 않는다.

## 리뷰와 완료

변경 목적, 실제 동작, 검증 근거와 남은 한계를 설명한다. PR을 사용하는 경우 리뷰 수정 push 이후 최신 commit의 CI와 미해결 리뷰를 다시 확인한다.

완료 조건을 충족하면 관련 문서를 현재 상태로 맞춘다. 계획의 상태를 Completed로 바꾸고 종료일을 기록한 뒤 completed로 이동한다. 미완료 필수 작업을 남겨 둔 채 계획을 완료로 표시하지 않는다. 취소가 결정된 계획은 [ExecPlan 운영 규칙](exec-plans/index.md#취소하기)에 따라 Cancelled로 기록하고 cancelled에 보관한다. 취소는 완료 실적으로 보고하지 않는다. 합의해서 미룬 항목만 [기술 부채](exec-plans/tech-debt-tracker.md)에 남긴다. 커밋·push·PR·배포 여부는 실제 수행 상태대로 보고한다.
