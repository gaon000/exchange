# exchange v1 단계별 구현 계획

상태: In Progress
종료일: 미종료
작성일: 2026-10-29 (Asia/Seoul)
현재 범위: P0~P4 완료. P5 HTTP/CLI와 실제 거래·과부하·저장 오류·응답 유실·프로세스 종료/복구 통합 검증을 구현했다. P6 부하 실행·원본 기록과 서버 구간·프로세스 자원 계측을 구현했다. 스냅샷/프로파일 서버 옵션을 연결했다. 새 프로세스 실행·환경/바이너리/원본 묶음을 연결했고 기준 측정은 남아 있다. 사용자는 별도 macOS/APFS 테스트 장비가 없으며 실제 전원 장애 검증을 미완료로 유지하도록 확인했다. 해당 필수 항목을 해제하지 않고 나머지 구현·실측을 계속한다.

[ExecPlan 운영 규칙](../index.md)을 따른다. 사용자는 계획대로 계속 구현하고 완료 작업마다 커밋하도록 요청했다. P4 완료는 HTTP API·실제 전원 장애·전체 성능 검증 완료가 아니다. P6의 수치 목표는 전체 경로의 초기 측정 후 정한다.

## Purpose / Big Picture

개발자가 로컬 컴퓨터에서 단일 거래쌍의 모의 주문·취소·조회를 수행하고, 프로세스 재시작 후 같은 주문·잔고·최초 응답을 복구하며, 영구 저장을 포함한 p99 지연 상한 내 최대 지속 처리량을 재현할 수 있게 한다.

[제품 명세](../../product-specs/exchange.md)가 범위·정책을, [상세 설계](../../design-docs/exchange-v1.md)가 처리 계약을 소유한다. 이 계획은 순서·산출물·검증과 실제 진행 기록을 소유한다. 실거래·입출금·수수료·UI·다중 거래쌍·분산 운영은 범위 밖이다.

## Surprises & Discoveries

- 2026-10-29 설계 문서 작성 시점: 문서만 있고 소스·go.mod·CI가 없었다. P0에서는 모듈·도구·probe만 추가했다.
- 2026-10-29 P0: PATH와 표준 위치에 Go가 없어 공식 Go 1.27.3을 체크섬 확인 후 `.tools/`에 준비했다. 시스템 전역 설정은 바꾸지 않았다.
- macOS 15.8/APFS에서 파일뿐 아니라 rename 후 디렉터리 F_FULLFSYNC도 성공했다. Go File.Sync는 ENOTSUP에서 fsync로 낮출 수 있어 cgo 시스템 호출을 통해 그 fallback을 금지하기로 했다.
- 명령 로그에는 승인뿐 아니라 잔고 부족 등의 업무 거절을 재현할 입력도 필요하다.
- 복구 시 유효하게 읽히는 마지막 그룹이 과거에 동기화 완료됐다고 단정할 수 없다. 복구한 로그의 내구성을 확정한 후 결과 응답을 허용해야 한다.
- 최초 생성 응답과 현재 주문 상태는 다르다. 재시도 캐시를 현재 주문 객체의 가변 참조로 구현하면 계약을 위반한다.
- P1에서 외부 테스트 패키지의 위치 기반 struct literal이 vet 진단을 발생시켜 필드명 표기로 수정했다. 이후 vet가 통과했다.
- P1 메모리 재시도는 새 순번을 소비하지 않는다. WAL 연결은 Lookup·pending 중복 제거를 기록 전에 수행하고 재생 후 appliedSeq를 확인해야 한다.
- P2는 완전한 미응답 그룹을 복구할 수 있지만 이전 sync 완료로 간주하지 않는다. Open/Replay와 ConfirmRecovery를 분리해 truncate·재동기화 전에는 append를 막는다.
- P2 프레임은 전체 header를 읽은 시점에 count와 payload 크기로 불가능한 길이·run 한도를 판정한다. EOF 근처의 불가능한 길이를 잘린 정상 꼬리로 낮추지 않는다.
- P3에서는 context 취소와 명령 취소를 분리했다. 응답 대기 슬롯은 해제하지만 큐/배치의 명령을 제거하지 않으며, runtime 종료 대기 timeout도 drain을 중단하지 않는다.
- P3 batch 바이트 한도에서 꺼낸 다음 명령 하나를 보관해야 FIFO를 유지할 수 있다. command channel 한도와 owner의 배치/추가 한 개 공간을 별도로 명시했다.
- P4에서는 snapshot 응답 대기 timeout과 사본 수명을 분리했다. 대기자가 없어져도 게시 중 사본을 유지하므로 동시 사본 제한을 응답 슬롯 수로 대신할 수 없다.
- P4 종료/오류 시 WAL뿐 아니라 snapshot worker까지 합류해야 run 잠금이 다음 프로세스에 너무 일찍 넘어가지 않는다. 파일 게시 후 owner 확인 전 종료한 경우 새 파일은 다음 복구에서 다시 검증한다.
- P5에서 net/http의 작은 응답 버퍼는 handler 반환 후 전송될 수 있음을 확인했다. 마지막 flush까지 HTTP 요청 슬롯을 유지하고, 느린 수신자에게 실제 write timeout이 발생하는지 별도 소켓으로 검사했다.
- P5에서 Go 1.27.3의 헤더 읽기 여유분과 body 없는 요청의 연결 감지 읽기를 확인했다. 실제 8 KiB 헤더 상한을 보정하고, GET의 결과 대기가 body timeout 때문에 조기 취소되지 않도록 분리했다.
- P5 CLI의 HTTP 종료를 먼저 기다리면 아직 배치 시간 제한을 기다리는 명령의 응답도 늦어진다. runtime drain을 함께 시작해 접수된 배치를 바로 닫고, HTTP 종료 제한과 저장 작업의 수명을 분리했다.
- P5 HTTP 장애 통합은 runtime의 외부 테스트 패키지와 `_test.go` bridge를 사용했다. API→runtime 의존 순환 없이 private 경계를 제어하며 일반 바이너리에 장애 옵션을 넣지 않는다. WAL 호출 내부 주입과 HTTP 통합의 저장 결과 adapter를 다른 증거로 기록한다.
- P6 요청 시각은 잘린 interval을 반복 더하지 않고 각 인덱스의 유리수 위치에서 계산한다. 실행 worker가 차거나 늦어진 요청은 큐에 숨기지 않고 미전송 표본으로 남긴다.
- P6 중복 응답이 원본보다 먼저 끝날 수 있다. 가장 먼저 완전하게 관찰한 결과를 고유 명령의 완료로 쓰되 최초 예정 시각·phase를 유지해야 워밍업 재시도와 빠른 중복이 측정 신규 주문 처리량을 부풀리지 않는다.
- P6 측정 구간 뒤에 도착한 성공은 지연과 cohort 결과에 남기되 고정 구간 처리량에는 더하지 않는다. timeout 지연은 실패 관찰 시각이며 서버 명령의 완료 시각이 아니다.
- P6 실제 HTTP client의 쓰기 callback은 실패 응답 뒤 실행될 수 있어 atomic cell로 관찰 시각만 복사한다. 잘린 HTTP 200은 완료 결과가 아니며 재시도 성공과 같은 결과로 집계하지 않는다.
- P6 서버 카운터·분포는 서로 다른 시점과 분모를 가진다. Write의 반환 bytes/2xx는 Flush 실패나 클라이언트 수신 성공과 다르며 WAL frame 시도 크기는 부분 실패 때 실제 파일 증가와 다르다. 관찰 구간·오류 수와 함께 해석한다.

## Outcomes & Retrospective

P4까지 생성/게시와 거래·종료가 겹쳐도 한 사본과 잠금 수명을 지키고 최신·이전·Genesis에서 같은 상태와 최초 결과를 복구했다. P5 HTTP 계층과 CLI에서 거래·조회·중복·경합·timeout·포화·저장 오류와 응답 전후 프로세스 종료/복구를 검증했다. P6 부하 실행·원본 기록과 서버/생성기 계측을 연결했다. 정상·snapshot·profiling 설정과 환경/원본 묶음을 연결했고 다음은 초기 측정과 성능 판정 조건 고정이다. 실제 전원 장애는 별도 장비가 없어 미검증이며 v1 전체 계획은 In Progress다.

## Context and Orientation

실제 프로젝트에는 go.mod/.go-version, scripts, config/examples, tools/storageprobe, cmd/exchange, cmd/loadgen과 internal/domain, internal/engine, internal/strictjson, internal/durable, internal/wal, internal/snapshot, internal/runtime, internal/api, internal/bench, internal/buildinfo, internal/telemetry가 있다. 나머지 예정 소스 경로는 [전체 구조](../../../ARCHITECTURE.md)의 표에서 구분한다.

개발 규칙은 [Development](../../development.md)와 [Workflow](../../workflow.md)를 따른다. 새 production dependency는 추가 전 확인하고, source를 변경하면 해당 테스트를 실행한다. 모든 변경은 feature branch에서 수행한다.

핵심 계약은 `snapshotSeq ≤ appliedSeq ≤ durableSeq`다. 큐 포화는 이번 시도의 미접수이고, 접수 후 timeout은 결과 미확정이다. 같은 키·같은 내용은 최초 결과를 반환하며, 초기 잔고는 새 실험에서만 지급한다.

## Plan of Work

의존 순서는 `P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7`이다. 단계마다 관련 설계·테스트·개발 명령을 같은 변경에서 갱신한다. 뒤 단계가 앞 단계의 검증 실패를 덮지 않는다.

### P0. 구현 계약과 환경 결정

완료: [개발 환경](../../development.md), [API 계약](../../design-docs/api-v1.md), [저장 형식](../../design-docs/storage-v1.md), [초기 fixture](../../../config/examples/local.json), [probe](../../../tools/storageprobe/main.go)에 반영했다. 아래는 원래 작업 범위이며 실제 증거는 Artifacts and Notes에 남긴다.

- 실제 Go 설치 경로·지원 버전·OS/CPU/메모리/파일 시스템을 확인하고 재현 가능한 toolchain 기준을 정한다. 현재 경로에서 Go가 없다는 사실을 구현 장애로 숨기지 않는다.
- 모듈 경로, 가격·수량 단위, 초기 총공급량, 최대 주문 금액·ID·본문 크기를 정한다.
- 제안 기본안인 로컬 HTTP/JSON의 적합성을 검토해 API 전송·필드·오류·계정 식별·runId 전달·조회 일관성 계약을 확정한다. 이는 현재 구현 또는 이미 합의된 wire 명세가 아니다.
- PlaceOrder·CancelOrder·조회 계약과 정규화 규칙, 최초 응답 형식·버전을 문서화한다. 로컬 테스트 계정 식별을 실제 서비스 인증으로 설명하지 않는다.
- WAL·스냅샷 형식의 버전/인코딩/프레임 한도, 데이터 디렉터리 단일 소유권, 파일·드라이브 캐시·디렉터리 동기화 방법을 정한다.
- 추가 라이브러리가 필요하면 목적·대안·영향을 제시하고 기존 승인 규칙을 따른다. 표준 라이브러리 우선이라는 계획을 의존성 설치 완료로 기록하지 않는다.

산출물: 실제 도구 기준, 계약 예시, 환경·내구성 가정, 결정 로그. 완료 조건: 금액 계산/정규화가 모호하지 않고, 대상 OS에서 필요한 동기화 경로의 구현·검증 방법이 정해짐. 성능 기준값은 P6에서 정하는 것으로 명시한다.

### P1. 결정적인 메모리 엔진

완료 경로: [internal/domain](../../../internal/domain/types.go), [internal/engine](../../../internal/engine/engine.go), 엔진 사례·독립 모델·fuzz·benchmark. Go 모듈·toolchain은 P0에서 준비했다. 아래는 수행한 범위이며 증거는 Artifacts and Notes에 있다.

- 정수 단위·ID·명령·결과·상태 타입과 overflow 검사를 구현한다.
- 초기 상태, 가격/FIFO 호가창, 주문 조회, 최대 예약·가격 차액 반환·부분 체결·취소·자기 거래 차단을 구현한다.
- 최초 결과를 가변 주문 객체와 분리한다. 엔진은 명시적으로 받은 명령·순번·입력만 사용하고 네트워크·디스크·벽시계에 의존하지 않는다.
- 작은 독립 기준 모델과 수작업 기대값을 만들고 무작위 명령마다 잔고·예약·수량 보존을 비교한다. 기준 모델은 최적화 엔진 코드를 그대로 복사하지 않는다.
- 엔진 단독 benchmark는 이 단계부터 보관할 수 있지만 전체 거래 API 성능으로 발표하지 않는다.

완료 조건: 상세 설계 V01~V06의 메모리 모델 시나리오 통과, 정수 경계·동일 입력 결정성·자산 보존 검증. 잘못된 입력 후 부분 상태 변경 없음.

### P2. 로그와 영구 저장 경계

완료 경로: [internal/wal](../../../internal/wal/store.go), [internal/durable](../../../internal/durable/darwin.go), [internal/strictjson](../../../internal/strictjson/strict.go). 아래는 수행한 범위이며 증거는 Artifacts and Notes에 있다.

- Genesis와 WAL의 버전·runId·순번·길이·체크섬·그룹 완료 표식을 구현한다.
- short write, 파일 생성/전환, 강한 동기화, 단일 디렉터리 잠금, sync 실패를 다룬다.

완료 조건: V07/V08/V12의 저장 계층 검증, 모든 바이트 절단 경계와 실패 위치에서 허용된 복구 또는 중단, 저장 실패 시 확정된 durableSeq를 잘못 전진시키지 않음. 플랫폼 검증의 실제 범위와 한계를 기록한다.

### P3. 단일 소유자 runtime과 응답 계약

완료 경로: [internal/runtime](../../../internal/runtime/runtime.go), [owner](../../../internal/runtime/owner.go), [query](../../../internal/runtime/query.go), [엔진 조회](../../../internal/engine/view.go). 아래는 수행한 범위이며 증거는 Artifacts and Notes에 있다.

- 제한된 큐, 순번, 개수/바이트/시간 기준 배치, 한 배치의 저장→적용→응답 흐름을 연결한다.
- 진행 중 키의 중복 합치기·대기자 한도·다른 내용 충돌·완료 결과 게시를 구현한다.
- 형식 거절과 업무 거절, 미접수와 결과 미확정을 분리한다. 연결 종료는 접수한 명령을 제거하지 않는다.
- 명령 경계의 조회 사본과 asOfSeq를 제공한다. 응답 송신은 업무 고루틴을 막지 않는다.
- 스냅샷 없이 Genesis부터 WAL 전부를 재생하는 최소 복구를 연결해 이 단계부터 재시작 계약을 검증한다.
- 정상 종료 drain과 오류 시 준비 상태 해제·처리 중단을 구현한다.

완료 조건: V04~V07/V10/V11 통과, 동기화 전에 성공 응답 없음, 적용 경계에서만 결과 게시, 중복 명령은 한 번만 실행, race detector에서 데이터 경합 없음. timeout 후 재시도 결과가 정상 실행과 일치.

### P4. 스냅샷과 전체 복구

완료 경로: [domain.Checkpoint](../../../internal/domain/checkpoint.go), [engine.Capture/Restore](../../../internal/engine/checkpoint.go), [snapshot 코덱](../../../internal/snapshot/codec.go)·[파일 게시](../../../internal/snapshot/publish.go)·[후보 파일 처리](../../../internal/snapshot/files.go), [runtime 기동 복구](../../../internal/runtime/recovery.go)·[실행 중 생성](../../../internal/runtime/snapshot.go)·[owner와 두 worker 종료](../../../internal/runtime/owner.go). 아래 범위를 계층 검사와 runtime 통합 검사로 확인했다.

- 한 명령 경계의 불변 상태 사본에 주문·잔고·우선순위·체결·최초 결과·설정·버전·snapshotSeq를 포함한다.
- 임시 파일 기록·동기화·정식 게시·메타데이터 동기화와 기존 정상 스냅샷 보존을 구현한다.
- 최신 정상 스냅샷+후속 WAL을 복구하고, 유효 tail과 복구 과정의 파일 변경을 영구 확정한 후 readiness를 연다.
- 기존 디렉터리의 초기화 금지, 잘못된 runId/버전 거절, 일반 재시작의 무재지급을 확인한다.
- 첫 버전은 WAL과 중복 결과를 보존한다. snapshot pause와 증가한 메모리는 이후 측정한다.

완료 조건: V07~V10/V12 통과. Genesis부터의 재생, 최신 스냅샷부터의 재생, 이전 스냅샷부터의 재생이 동일한 상태·최초 결과를 만든다. 불완전한 스냅샷이 유일한 복구 근거가 되지 않는다.

### P5. 공개 API와 장애·경합 검증

구현 경로: [internal/api](../../../internal/api/server.go), [cmd/exchange](../../../cmd/exchange/main.go), 각 패키지의 handler·실제 소켓·APFS/runtime·프로세스 통합 테스트와 [HTTP 장애 통합](../../../internal/runtime/http_fault_native_test.go). 테스트는 패키지와 함께 두며 별도 tests/integration/fault 폴더는 만들지 않았다. 아래 소프트웨어 검증을 연결했고 실제 전원 장애는 미완료다.

- P0 계약의 주문·취소·주문/잔고/호가/체결 조회·결과 조회를 제공하고 필드·계정·권한·크기 검사를 연결한다.
- loopback 테스트 계정으로 실제 네트워크 요청을 보내 응답 유실·중복·취소 경합·큐 포화를 확인한다.
- write/sync/apply/response 및 snapshot 게시 지점에 종료·오류를 주입한다. 원본 입력과 기대 상태를 따로 남겨 복구 결과와 비교한다.
- 파일 시스템 호출 오류/프로세스 kill 검증과 실제 OS·전원 장애 검증을 분리한다.
- 전원 장애 검증은 데이터 손실을 허용한 전용 환경에서 수행할 계획과 실행 범위를 확인한다. 사용자의 개발 컴퓨터를 임의로 종료하지 않는다. 실제 조건을 확보하지 못하면 해당 검증은 미완료로 남긴다.

완료 조건: V01~V12의 API/파일/복구 통합 시나리오 통과와 증거 기록. 같은 ID로 기존 결과를 조회·재시도할 수 있음. 실제 전원 장애 항목이 미검증이면 이를 통과나 전체 복구 보장 달성으로 보고하지 않는다.

### P6. 부하 생성기와 기준 측정

구현된 경로: `internal/bench/`의 부하 실행, `cmd/loadgen/`의 CLI/원본 기록, `internal/buildinfo/`의 바이너리 출처, `internal/telemetry/`와 runtime/wal/api의 구간/자원 계측 및 `cmd/exchange/metrics.go`의 기록 worker. - 여러 테스트 계정과 고정 seed·초기 잔고·호가 깊이를 사용하는 재현 부하를 만든다. 실험 초기화와 일반 재시작을 명확히 분리한다.
- 응답을 기다려 다음 요청 속도를 자동으로 낮추는 부하만 사용하지 않는다. 예정 발사율을 유지하는 부하에서 예정/실제 발사 시각·응답·timeout을 기록하고 생성기 자체 지연을 식별한다.
- 추가·체결·취소·중복·업무 거절·과부하를 분리하고, 성공한 고유 신규 주문 처리량과 p50/p95/p99, 최대값, timeout·거절률을 산출한다.
- 큐 대기·배치 대기·로그 쓰기/동기화·엔진 적용·응답 비용과 CPU·메모리·GC·로그 증가를 측정한다.
- 정상 상태와 스냅샷 생성 중 상태, 프로파일러 유무를 구분한다.
- 초기 측정 후 p99 상한, 허용 과부하 거절·timeout 비율, 워밍업/지속 시간, 반복 수, 계정 수·집중도·주문 크기·취소/체결 비율·호가 깊이·데이터 크기를 문서로 고정한다. 이후 최적화 결과를 보고 목표값을 유리하게 바꾸지 않는다.

완료 조건: 동일 조건을 재현하는 방법과 측정 원본이 존재하며, 서버보다 생성기가 먼저 포화되는 경우를 감지함. 측정 제외·미완료 요청을 숨기지 않고 지연 상한과 실패율 조건 아래 기준 지속 처리량을 기록함.

## Idempotence and Recovery

- 구현 시작 시 브랜치·작업 트리·실제 경로를 재확인하고 이미 구현된 단계를 초기화하지 않는다.
- 테스트는 폐기 가능한 별도 디렉터리와 고유 runId를 사용한다. 사용자 데이터 디렉터리에 reset·재초기화를 수행하지 않는다.
- 기존 로그 버전·설정이 다르면 자동 수정하지 않고 중단한다. 실패 로그와 재현 입력을 보존한다.
- 단계가 실패하면 마지막 검증된 구현에서 재현하고 최소 수정한다. 구조 변경 때도 원래 순번·최초 결과·예약 보존 조건은 유지한다.
- 완료 시 계획 본문의 상태·종료일을 갱신하고 completed로 이동하며 양쪽 index와 상대 링크를 고친다.
