## Surprises & Discoveries

- 기존 experiment는 부하 생성기 종료 직후 서버를 종료한다. 이번에는 종료 전 전체 상태 조회가 필요해 기존 서버·생성기를 실행하는 실험 전용 스크립트를 원본 묶음에 보존한다. 애플리케이션 소스는 변경하지 않는다.
- 최초 결과와 현재 주문은 별도다. 응답받은 모든 명령의 원본 응답 SHA-256을 GET 결과와 대조하고, 전체 조회 대조 후에만 일부 중복 POST를 수행한다.
- 끔 조건에서 생성기 발사 지연 한도 50ms를 넘긴 14건이 미전송되어 measurementValid=false였다. 완료 marker가 없는 실패 실행도 원본에서 재집계하도록 오프라인 분석기를 보완했고, 실패·누락을 그대로 보고했다.
- 켬 조건은 미전송 0이지만 마지막 1분 요청 p99가 38.309ms였다. 복구는 끔 1.223초·켬 4.713초로 켬 쪽이 느렸다. 1회·공유 호스트 실험으로 원인을 확정하지 않는다.

## Outcomes & Retrospective

요청한 두 10분 부하와 복구·비교를 완료했다. [보고서](../../benchmarks/soak-10m-snapshot-comparison.md)에 전체/구간별 지연·자원·복구와 원본을 기록했다. 끔/켬에서 고유 명령 51,373/51,385개, 주문 45,270/45,280개, 체결 12,114/12,117개와 모든 계정 잔고가 재시작 전후 일치했다. 각각 기존 명령 12개 재시도 후 전체 조회와 WAL hash도 유지됐다.

전체 요청 p99는 9.207/17.556ms, 측정 종료 전 peak RSS는 106.38/197.22MiB였다. 5초 구간별 20ms 기준을 12/26개 구간에서 넘겨 두 조건 모두 지속 성능 기준 통과로 보고하지 않는다. 각 조건 1회이며 실제 전원 장애는 보류다. 애플리케이션 소스·의존성은 변경하지 않았고 커밋·병합·push는 수행하지 않았다.

## Context and Orientation

기준 commit은 3b5a6f5다. config/benchmarks/config-v1.json의 초기 잔고와 200만 명령 한도를 유지한다. 기존 부하 설정에서 namespace=soak-v1, requestsPerSecond=100, durationNanos=600000000000만 변경한다. 예정 시도는 워밍업 500+측정 60,000개, 별도 준비 주문은 20개다.

## Plan of Work

1. 기존 exchange/loadgen의 같은 clean 바이너리와 설정을 두 조건에 사용한다.
2. 실제 loopback/APFS 거래를 실행하고 오류·누락을 포함한 모든 원본 표본과 계측을 보존한다.
3. 부하 종료 후 모든 계정·주문·명령 결과와 전체 체결 페이지·호가를 조회한다. 자산 공급량과 명령 순번을 확인한다.
4. 소유 서버를 SIGTERM으로 종료하고 같은 run을 다시 연다. process 시작→ready+health 성공 시간을 측정하고 실제 snapshot 선택/재생 수를 기록한다.
5. 재시도 전 전체 조회를 비교한 뒤 원래 명령 일부를 재전송한다. 전체 상태와 WAL 해시 불변을 확인하고 서버 종료·포트 해제를 확인한다.
6. 원본에서 일반/5초/60초 지연·오류를 재집계하고 측정 구간의 메모리·CPU·GC·큐·스냅샷 비용을 비교한다.
