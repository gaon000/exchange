# 호스트 관찰과 현재 기준 재측정

2026-11-06, clean `ca74b53916f8a583a6ae9754968a7ad6a63be49a` 생산 바이너리로 기존 [P6 고정 조건](p6-baseline.md#고정-비교-조건-v1)의 두 과거 채택점을 각각 세 번 확인했다. **정상 29,000 requests/s는 0/3, snapshot 3,000 requests/s는 2/3 통과였다. 이번에는 두 조건 모두 qualified=false이며 새 처리량 기준으로 채택하지 않는다.** 과거 채택 결과를 지우거나 현재도 항상 재현된다고 해석하지 않는다.

[기계 판독 결과](20261106-controlled-baseline.json)에 모든 실행의 판정·오류·창별 분포/큐·자원·환경·source/binary/원본 hash를 보존한다. [실행 도구 안내](../controlled-baseline.md)에 재현 명령과 gate·예산을 기록한다. 실제 전원 장애와 10분 실험은 수행하지 않았다.

## 조건과 호스트

워밍업 5초·본 측정 20초·서버 계측 500ms·snapshot 5초·최소 반복 3회·전체/5초 창 20ms·생성기 및 비업무 오류 0의 기존 기준을 유지했다. 초기 계정·잔고·seed 17·입력 비율·실행 한도는 기존 fixture와 같다. 생산 바이너리는 모두 `vcs.modified=false`와 고정 SHA-256을 확인했다. 실행 제어 Python 도구는 별도 feature branch에서 개발했으며 protocol에 source hash를 기록했다.

Go 1.27.3, macOS 15.8 arm64·Apple M3 Pro·논리 CPU 11개·RAM 18GiB·로컬 APFS다. GOMAXPROCS=11, GOGC=100, GOMEMLIMIT=off를 명시하고 GODEBUG를 제거했다. trace·profile·생성기 진단은 껐다. 과거의 암묵적 Go 기본값과 이번에 명시한 실행 환경을 같은 series로 혼합하지 않는다.

순서는 정상1→snapshot1→snapshot2→정상2→정상3→snapshot3이며 실행 후 30초 cooldown을 적용했다. 각 실행 전 AC 전원·thermal 응답을 기록했다. thermal 경고는 없었지만 CPU power status가 기록되지 않았다는 응답을 CPU 주파수의 완전한 보장으로 해석하지 않는다.

초기 strict smoke 세 묶음의 유휴 검사 9개가 모두 실패해 주문 부하를 시작하지 않았다. busy 중앙값은 25.0~51.0%, 최대는 25.0~62.0%였고 macOS 저장 공간 분석/정리 프로세스의 높은 CPU 사용을 읽기 전용으로 관찰했다. 원인을 해당 프로세스만으로 확정하지 않았다. 사용자가 다른 작업을 줄이겠다고 응답한 뒤 기준 실행을 진행했다. 별도의 6초 경로 smoke는 유휴 실패를 accepted=false·enforced=false로 기록한 채 실제 거래/원본/판정 경로만 확인했다. 그 smoke는 기준 실험이 아니다.

본 실행은 매회 최소 10개 1초 관측에서 busy 중앙값 ≤15%, 최대 ≤30%를 만족해야 시작했다. 채택한 시작 관측의 중앙값은 4.0~15.0%, 최대는 8.0~24.0%였다. 정상1과 snapshot1은 첫 gate 실패도 보존했고 두 번째 관측에서 시작했다. 측정 중 다른 로컬 빌드·테스트를 실행하지 않았고 다른 앱·시스템 프로세스를 강제 종료하거나 OS 설정을 바꾸지 않았다.

시작 전 유휴는 실행 중의 전용 자원·열·캐시·OS/runtime 스케줄링을 보장하지 않는다. 서버/생성기와 호스트 관찰자는 같은 장비를 공유하며 관찰 비용도 수치화하지 않았다. 생애 host busy 중앙값은 정상 46.5~50.5%, snapshot 12.0~17.0%였고 자체 부하도 포함한다. 이 값으로 외부 프로세스의 기여나 특정 원인을 분리하지 않는다.

## 여섯 실행

미전송은 워밍업/본 측정을 분리한다. p99와 신규 승인/s는 본 측정 cohort다. 마지막 열의 창별 최악은 요청/예정 시각 p99 중 큰 값이다.

정상1의 미전송은 CAPACITY 31,199건과 LATE 3,643건, 정상2는 CAPACITY 9,223건이다. 정상3은 본 측정 누락이 없어도 워밍업 CAPACITY 921건과 지연 초과로 탈락한다. 실패한 세 실행의 관찰 처리량을 유효한 지속 처리량으로 채택하지 않는다.

snapshot2는 마지막 본 측정 5초 창(예정 epoch 20~25초)에서 요청 p99 20.628375ms, 예정 p99 20.685959ms로 탈락했다. 해당 창의 계측 표본은 10개, queue 평균 2.3·최대 6이었다. 전체 요청 p99가 9.236ms이고 미전송이 없다는 이유로 창 기준을 해제하지 않는다. 세 번의 측정과 겹친 완료 snapshot은 각각 4개였다.

같은 조건·소스·binary의 모든 반복이 통과해야 한다. 정상 그룹은 0/3, snapshot 그룹은 2/3으로 두 그룹 모두 qualified=false다. 통과한 snapshot 두 개만 골라 반복을 추가하거나 실패를 교체하지 않았다. 다른 rate·다른 상태 크기의 정상과 snapshot을 같은 상태에서의 snapshot 비용 비율로 계산하지 않는다.

## 자원과 검증

서버 생애 CPU는 정상 44.85~50.17 CPU초, snapshot 7.82~7.95초였다. 서버 생애 peak RSS는 정상 1,290~1,348MiB, snapshot 211~236MiB였다. 본 측정 구간 전용 자원이나 두 프로세스의 동시 합계로 해석하지 않는다.

관찰된 소유 프로세스 RSS 합계 최대는 2.412GiB, 새 묶음 관찰 최대는 3.283GiB, 여유 디스크 최소는 14.084GiB였다. 사전의 단일 RSS 2GiB·합계 3GiB·묶음 4GiB·여유 8GiB 한도 위반은 없었다. 주기 사이 순간값을 보장하는 제한은 아니다.

고정 benchreport의 최초 판정과 현재 source로 별도 재실행한 판정의 cases/groups가 모두 일치했다. 완료 root inventory와 경로 smoke inventory를 검증했고 초기 실패 묶음도 completed=false로 보존했다. parent 완료 표시는 원본 수집/검증 완료이며 성능 채택을 뜻하지 않는다. 원본·frozen binary·명령·source hash·호스트 관측은 Git 제외 `var/controlled-baseline-reference`에 있고, 사후 재집계는 `var/controlled-baseline-recheck.json`에 있다.

도구 회귀는 Python 일반/`-O` 각각 25개, 전체 portable Go 205개·native race 237개와 기존 실제 비교/복구/변조 smoke를 통과했다. reference quiet 실패 시 부하 프로세스를 시작하지 않음, 소유 프로세스만 추적, 자원 한도·dirty binary·신호/강제 종료·부분 실패 보존도 검사했다. 비교 기능의 master 커밋 ca74b53은 실제 [GitHub CI](https://github.com/gaon000/exchange/actions/runs/42190355036)를 통과했다. 이번 기준 측정 도구·결과 변경의 원격 CI와 구분한다.

현재의 결론은 **두 과거 채택점을 이번 조건에서 재현하지 못했다**는 것이다. 다음에는 기존 실패를 보존하면서 더 낮은 정상/snapshot 요청률에서 새 3회 그룹을 사전에 정해 유효한 작업점을 찾는 것이 적절하다. 이 결과만으로 거래 엔진·SSD·Go runtime 중 하나를 원인으로 확정하거나 구현을 교체하지 않는다. 실제 전원 장애 검증은 계속 미완료·보류다.
