# 타이머 trace 켬·끔 대조

현재 저장소에서 다시 실행·검증·분석하는 명령은 [실험 도구 안내](../diagnostic-tools.md)를 따른다. 아래 경로·명령은 당시 측정 근거로 보존한다.

2026-11-06, 같은 바이너리에서 trace를 켜거나 끄고 타이머 단독·worker 전달을 각각 10분 스케줄로 실행했다. **trace를 끈 worker 조건에서도 타이머 종료가 예정 대비 55.610ms 늦어 50ms 한도 초과 1건이 발생했다. 선택적 trace 없이도 긴 지연은 발생할 수 있다.** 이번 켬 조건에서 p99·초과 수가 더 컸지만, 시점별 호스트 상태가 달라 그 차이를 trace의 인과 효과로 확정하지 않는다.

[기계 판독 결과](20261106-timer-trace-control-report.json)에 네 실행·전체 실패 표본·선택 trace/구간·입력 해시를 보존한다. 전체 240,000개 표본과 480개 5초 구간, 두 trace의 전체 분석은 Git 제외 `var/timer-trace-control-20261106.vfehlj86`에 있다. [이전 분리 실험](timer-os-io-diagnosis.md)의 결과를 대체하지 않고 계측 영향의 대조 근거를 추가한다.

## 동일 조건과 차이

기반 revision은 `74a1206af94ada42eabbc5440e651c779bf181e5`다. 기존 feature branch·미커밋 문서를 보존하고 task-local 도구에 `--trace` 옵션만 추가했다. production source·dependency·거래/저장 계약은 변경하지 않았다. 같은 macOS 15.8 arm64/APFS, M3 Pro 11 CPU/18GiB, Go 1.27.3에서 한 번 빌드한 바이너리를 네 실행에 사용하고 hash를 매회 확인했다.

| 항목 | 실행 조건 |
| --- | --- |
| 순서 | 타이머 단독 끔→단독 켬→worker 켬→worker 끔 |
| 계획 | 각 100/s·10ms 간격·60,000개 예정 시각, 명목 600초 스케줄 |
| 타이머 | 기존 NewTimer/select와 20ms 뒤 epoch, 같은 시각 관찰·표본 배열 |
| worker | 2,048개 고루틴, 전달 대기열 없음, 실제 도착 시각만 기록 |
| 지연 판정 | 전달 전 또는 worker의 예정 대비 지연이 50ms를 초과하면 실패 표시 |
| trace 끔 | runtime trace·clock Log·지연 fmt/Log를 모두 생략, 파일 없음·traceBytes=0 |
| trace 켬 | 앞의 수집을 함께 활성화, 파일 128MiB 한도 |
| 공통 출력 | 표본 JSON은 종료 후 기록. 준비·warmup·HTTP·엔진·WAL/snapshot 작업 없음 |
| 실행 사이 | 종료·표본 저장 후 30초 유휴 |
| 감시 | 5초 간격, 최소 디스크 여유 8GiB·RSS 2GiB·실행 제한 660초 |

trace 끔에서도 타임스탬프·메모리 기록·같은 자원 감시는 남는다. 완전한 무계측 실행이 아니다. treatment는 trace backend만이 아니라 clock anchor·조건부 문자열 생성/Log까지 포함한다. 켬의 trace 파일 쓰기는 실행 중 발생한다. 이전 도구는 항상 켰지만 새 도구의 기본값은 false이고 네 실행 모두 실제 값을 명시했다.

## 결과

모든 지연은 ms이며 각 실행의 60,000개 예정 표본을 분모로 한다. worker가 관찰되지 않은 표본은 worker 분위수에 0으로 넣지 않는다.

| 조건 | 타이머 종료 p99 | 타이머 종료 최대 | 전달 전 50ms 초과 | worker 예정 기준 p99 / 최대 | worker 50ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 단독·끔 | 1.154 | 43.895 | 0 | 해당 없음 | 해당 없음 |
| 단독·켬 | 4.222 | 131.543 | 22 | 해당 없음 | 해당 없음 |
| worker·켬 | 5.822 | 92.057 | 25 | 5.735 / 72.402 | 2 |
| worker·끔 | 2.742 | 55.610 | 1 | 2.796 / 45.892 | 0 |

전달 전 50ms 초과는 worker로 보내지 않는다. 따라서 worker 도착 표본은 켬 59,975개·끔 59,999개다. capacity 실패는 모두 0이다. 켬의 worker 실패 2건은 도착한 표본 중 예정 대비 50ms를 넘은 경우다. 이 도구는 실제 주문을 보내지 않으므로 이 수를 실제 거래소 주문 미전송 건수로 부르지 않는다. suite PASSED는 네 실행과 산출물 완료를 뜻하며 모든 시각이 한도를 만족했다는 뜻은 아니다.

worker 전달 전 관찰→worker의 p99/최대는 켬 0.059/57.145ms, 끔 0.065/6.045ms였다. 해당 구간에는 실제 채널 전달 전 시간도 들어 있으므로 worker runnable 대기 시간과 같지 않다. 타이머 종료 10ms 초과는 실행 순서대로 23/193/243/46개였다. 실패·느린 표본을 제외하거나 재실행 성공으로 교체하지 않았다.

## trace 없는 한도 초과 사례

worker·끔의 index 38026은 예정 380.260초, 대기 시작 380.251151333초, 종료 380.315609958초였다. 대기는 약 64.459ms였고 종료가 예정 대비 55.609958ms 늦어 전달 전 검사에서 표시됐다. worker로 보내지 않아 worker 시각은 -1이다.

이 실행에는 trace 파일이 없고 traceBytes=0이며 지연 fmt/Log도 실행되지 않는다. 따라서 선택 trace가 이 사례에 필수 조건이라는 설명은 성립하지 않는다. 여전히 기본 시각 관찰·표본 기록·자원 감시가 있으며 OS/runtime/스레드 스케줄링 중 무엇이 지연을 만들었는지는 이 사례로 구분하지 못한다. 이전의 worker 검사 초과와 이번 전달 전 초과의 근본 원인이 같다고 주장하지 않는다.

## 해석의 한계

각 조건은 1회이며 순서는 무작위가 아니다. 다른 사용자 프로세스·온도·캐시·호스트 부하는 통제하지 않았다. 관찰한 디스크 여유 범위는 단독 끔 약 15.89~16.91GiB, 단독 켬 13.10~16.83GiB, worker 켬 10.20~14.48GiB, worker 끔 13.50~14.37GiB였다. 큰 변화의 원인을 추적하지 않았으며 우리 도구의 trace bytes와 같은 양으로 해석하지 않는다. 이 변화 자체가 특정 CPU/I/O 원인의 증명도 아니다.

worker·켬에서는 UTC 경과−trace 경과의 끝점 차이가 약 -2,056.449ms였다. 자원 guard의 인접 UTC/monotonic 경과 차이에서도 약 -2.059초 변화가 보였다. 원인을 확정하지 않고 기록하며 **지연과 실행 한도는 모두 monotonic으로 계산**했다. 다른 조건과 UTC로 짧은 사건을 일대일 대조하지 않는다. 단독 켬의 trace 끝점 차이는 약 +2.647ms였고, 어느 끝점 차이도 전체 구간 오차 상한을 뜻하지 않는다.

이번 두 쌍에서 켬의 꼬리 지연이 더 컸다는 관찰은 남지만, 호스트 상태·순서가 달라 순수 계측 비용의 수치나 계측 제거의 개선율로 채택하지 않는다. 거래 엔진이나 타이머 구현을 변경할 근거로 확대하지 않는다.

## 검증과 보관

관련 타이머 경계·worker 합류/취소 테스트 2개를 race로 통과했다. 실제 CLI 2초 예비 실행에서 off의 파일 부재·0 bytes, on의 실제 trace와 scheduler profile parser를 확인했다. 본 실행 240,000개 표본의 index·예정 간격·경계 순서·실패 판정을 재계산했고, 480개 5초 구간을 집계했다. 두 on trace는 전체 parser로 읽고 모든 scheduler/worker 표시의 index·offset·delay와 원본의 일치, 표시 누락/중복 부재를 확인했다. 두 off 조건은 파일 부재와 metadata를 검증했다.

원본에는 같은 바이너리·Go 소스·실행 인자·환경·protocol·자원 guard·표본·trace·분석·해시를 보존한다. 실행은 해당 parent의 `suite.py`, 전체 분석은 `analyze.py`, Git용 선택 결과는 `build_report.py` 순서다. 기존 case 재사용을 거절하고 분석 출력이 있으면 bytes를 대조한다. 재실험은 새 parent에서 환경·protocol을 다시 고정해야 한다.

추적 변경은 문서·선택 집계뿐이며 production source 변경은 없다. 별도 거래 부하나 새 복구 시험은 이번에 수행하지 않았다. 기존 복구 결과는 각 당시 보고서의 근거로 유지한다. 관리자 권한이 필요한 커널 I/O 추적과 실제 전원 장애는 기존 미확보·보류 상태다. 2026-11-06 실험 완료 당시에는 커밋·머지·push와 새 GitHub CI 실행을 하지 않았다.

다음 진단은 호스트 조건을 더 통제한 반복 실행에서 trace 계측의 영향을 분리하는 것이다. 현재까지는 trace 비활성만으로 50ms 한도가 보장되지 않는다는 근거를 확보했다.
