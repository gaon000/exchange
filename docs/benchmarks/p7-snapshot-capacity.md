# P7 스냅샷 사용 시 처리 한계

상태: 측정·보고 완료 — 기준 구현의 스냅샷 조건에서 3,000 requests/s를 3회 채택. 실제 전원 장애 검증과 전체 계획은 미완료다.
측정일: 2026-10-29 (Asia/Seoul).

## 목적과 고정 조건

[P6](p6-baseline.md)는 정상 29,000 requests/s를 세 번 채택했지만, 스냅샷을 켠 같은 부하는 세 번 모두 탈락했다. [정렬 이동 후보](p7-snapshot-sorting.md)도 채택하지 않고 기준 구현으로 복원했다. 이 측정은 아직 확인하지 않은 **기준 구현의 스냅샷 처리 한계**를 찾는다. 후보를 다시 채택하거나 지연 기준을 완화하는 실험이 아니다.

[고정 조건 v1](p6-baseline.md#고정-비교-조건-v1)에 따라 요청률만 탐색 변수로 변경했다. 전체/5초 창 p99 20ms, 오류·누락 0, 워밍업 5초·측정 20초, 최소 3회 독립 반복, seed 17·입력 비율·초기 자금·기본 서버 설정·500ms 계측을 유지했다. 스냅샷은 5초 주기, 측정과 겹친 완료 이벤트 최소 2개가 필요하다. 각 실행 전에 30초 유휴 시간을 두고 실험 종료 후 원본을 재집계했다.

서버·생성기·실행기·판정 도구 모두 P6의 clean `58836215ccbdf5171ac351d6b633b692366e0a17` 바이너리다. SHA-256, criteria/input hash와 snapshot series가 P6와 동일하다. 호스트는 같은 Apple M3 Pro·18GiB, macOS 15.8/APFS, Go 1.27.3이며 서버와 생성기를 함께 실행했다. 전역 시스템 설정이나 다른 사용자 프로세스를 변경하지 않았다.

실행 전 protocol.json에 4,000/s 시작, 기존 29,000/s 실패를 상한으로 하는 탐색, 1,000/s 간격, 최고 통과점의 3회 반복, 실패 시 하향 탐색, 최대 24회에서 미완료 보고할 규칙을 기록했다. 실제로는 4,000 → 2,000 → 3,000 → 3,000 → 3,000의 다섯 실행으로 끝났으며 실패한 반복을 제외하지 않았다.

## 결과

예정 p99는 승인된 고유 신규 주문의 원래 예정 시각 기준이다. 창별 판정은 각 창의 전체 시도 예정 지연도 검사하므로 전체 p99만으로 통과를 판단하지 않는다.

| 예정 요청/s | 반복 | 고유 신규 승인/s | 요청 p99 ms | 예정 p99 ms | 최악 창 요청/예정 p99 ms | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| 4,000 | 1 | 2,593.40 | 12.490 | 12.968 | 28.689 / 28.746 | WINDOW_3_P99 탈락 |
| 2,000 | 1 | 1,297.90 | 10.006 | 10.757 | 11.195 / 11.268 | 단일 통과, 반복 부족 |
| 3,000 | 1 | 1,948.80 | 9.746 | 10.510 | 18.474 / 18.532 | 통과 |
| 3,000 | 2 | 1,948.55 | 10.690 | 11.231 | 15.929 / 16.003 | 통과 |
| 3,000 | 3 | 1,948.60 | 9.964 | 10.505 | 12.210 / 12.231 | 통과·3회 채택 |

모든 실행의 워밍업/측정에서 생성기 누락·과부하·timeout·미해결 UNKNOWN은 0이었다. 측정과 겹친 스냅샷 완료는 매회 4개였다. 3,000/s의 첫/마지막 창 평균 command queue는 각각 2.9/3.2, 1.9/4.2, 2.6/2.6으로 증가 한도 64개 이내였다. 전체 비업무 오류·계측 수 조건도 통과했다. 세 번 통과한 3,000/s만 qualified=true이며, 바로 위 4,000/s의 실패를 보존했다. 이는 관찰한 1,000/s 간격의 채택점이고 모든 가능한 요청률의 전역 최대를 증명한 것은 아니다.

채택점의 요청 p50은 4.271~4.386ms, p95는 7.330~7.851ms, 최대값은 55.090~66.126ms였다. p99 통과는 모든 요청의 20ms 보장이 아니다. 성공 취소는 66.30~66.45/s, 체결은 598.30~600.05/s이며 중복·업무 거절을 신규 주문 처리량에 합산하지 않았다.

## 상태 크기와 스냅샷 비용

3,000/s의 서버 종료 appliedSeq는 매회 63,711이었다. WAL은 14,231,675~14,248,887bytes, peak RSS는 237.17~238.09MiB, 마지막 Go live heap은 106.20~108.02MiB였다. 서버 생애 CPU는 9.35~9.86 CPU초, GC 누적 CPU는 1.91~2.05초였다. 서버 생애/누적/peak 관찰을 측정 구간 전용 값으로 해석하지 않는다.

| 3,000/s 반복 | capture 최대 ms | publish 최대 ms | capture 횟수 |
| --- | --- | --- | --- |
| 1 | 60.286 | 996.358 | 5 |
| 2 | 58.420 | 984.805 | 5 |
| 3 | 49.560 | 955.872 | 5 |

현재 capture는 owner의 복사와 정렬을 포함하고 publish는 별도 worker의 저장 구간이다. 서버 생애에 5회 생성했으며, 위의 측정 교집합 완료 4회와 분모가 다르다. 4,000/s의 capture 최대는 65.753ms, 요청 최대는 75.762ms였다. 이 관찰만으로 각 지연 표본의 원인을 확정하지 않는다.

요청률을 낮추면 25초 동안 쌓이는 주문·최초 결과·체결 이력도 작아진다. 그러므로 정상 29,000/s와 스냅샷 3,000/s의 차이를 같은 상태 크기에서의 스냅샷 비용 비율로 계산하면 안 된다. 고정 상태 크기나 장시간 무제한 실행의 성능은 별도 검증 대상이다. 현재 상한·이력 보존 계약을 바꾸거나 오래된 결과를 지우지 않았다.

## 재현 자료와 보관

[기계 판독 결과](20261029-p7-snapshot-capacity.json)에 다섯 실행 전체, 사전 protocol, 원본 재집계 판정, 구간별 지연/큐, 서버·생성기 자원, 스냅샷 이벤트와 주요 원본 해시를 보존했다. 누락된 새 실험은 없으며 P6의 과거 29,000/s 세 번 실패는 [기존 결과](20261029-p6-baseline.json)에 그대로 있다. 보고서 파일 작성 후 편의 출력에서 RSS 정수 문자열 변환 오류가 한 번 발생했으나, 작성된 보고서를 원본과 대조한 뒤 출력 변환만 수정했다. 실험을 재실행하거나 결과를 덮어쓰지 않았다.

원본 생성 경로는 Git 제외 `var/p7-snapshot-capacity-6a5f8szg/`였다. 종료 후 202개 항목의 종류·권한·크기·SHA-256을 압축본과 비교하고 원본이 변경되지 않았는지 확인한 뒤 비압축 사본만 정리했다. [보관 메타데이터](20261029-p7-snapshot-capacity-archive.json)에 압축본과 검증 receipt의 경로·해시가 있다. 원본 표본·WAL·snapshot·실행 바이너리·탐색/재집계 스크립트를 포함한다.

복원할 때는 메타데이터의 SHA-256과 여유 공간, 대상 디렉터리가 없음을 확인한 뒤 저장소 루트에서 실행한다.

```sh
tar -xzf var/archives/p7-snapshot-capacity-6a5f8szg.tar.gz -C var
```

큰 원본 압축본은 로컬 보관이므로 저장소 clone만으로 원본 표본을 얻을 수 없다. 요약 JSON·해시·판정 문서는 Git에 포함한다. 이번 작업은 소스 변경 없이 고정 바이너리를 측정한 것으로, 전체 race/vet/build가 통과한 기준 구현을 변경하지 않았다.

## 전체 결과와 남은 조건

현재 자료가 뒷받침하는 값은 **정상 조건 29,000 requests/s의 과거 3회 채택**, **스냅샷 조건 3,000 requests/s의 이번 3회 채택**이다. 정상 고부하 대조의 일부 실패와 정렬 이동 후보의 미채택도 함께 보고한다. 완전히 통제하지 않은 개발 컴퓨터에서의 유한 실험 결과이며 항상 재현되는 서비스 SLA나 성능 개선 달성으로 주장하지 않는다.

이 결과로 정상·스냅샷 조건을 구분한 처리량 보고를 보완했다. 성능 후보를 검증하고 채택하지 않은 결론은 유지한다. 실제 OS·전원 장애 후 성공 응답 복구는 별도 장비가 없어 미검증이다. 사용자 확인대로 해당 필수 조건을 유지하며 전체 계획을 완료로 표시하지 않는다.
