끔 조건의 미전송 14건은 부하 생성기가 50ms 발사 지연 한도를 넘긴 결과다. 워밍업의 미전송은 두 조건 모두 0이다. 미전송을 거래 거절이나 성공으로 세지 않았으며, 끔 조건의 지연 분위수는 실제 전송한 요청에 대한 값이다. loadgen은 원본을 남긴 뒤 종료 코드 1과 `GENERATOR_MISSED_REQUESTS`를 기록했다. 실패 실행을 제거하거나 재실행한 성공 사례로 대체하지 않았다.

켬 조건은 60,000건의 유효한 측정 표본을 얻었지만 전체 p99만 보고 지연 기준 통과로 판정할 수 없다. 마지막 세 1분 구간의 p99가 각각 20.283, 27.568, 38.309ms로 증가했다. 5초 구간별 판정도 미달이다. 따라서 두 조건 모두 지속 성능 기준을 통과했다고 보고하지 않는다.

CPU 증분은 측정 시작/끝에 가장 가까운 직전 계측을 사용했다. 실제 표본 간격은 각각 600.001초·600.456초로, 정확히 600초의 전용 CPU 계측으로 해석하지 않는다. peak RSS는 측정 종료 전에 읽은 생애 최대값으로 워밍업도 포함한다. 측정 뒤 전체 조회·재시작 검증의 자원 비용은 위 부하 비교에서 제외했다.

켬 조건에서 측정과 겹친 스냅샷은 모두 COMPLETED였고 저장·스냅샷 오류는 0이다. 해당 스냅샷의 최대 전체 소요 시간은 약 1,711.85ms였다. 마지막 측정 표본의 누적 capture 최대는 154.07ms, publish 최대는 1,658.14ms다. 두 최대값은 같은 스냅샷을 가리킨다고 보장하지 않는다.

이력 보존에 따라 두 조건의 상태와 메모리가 증가했다. 켬 조건의 추가 메모리·GC CPU·후반 지연 증가가 관찰됐으나, 이 한 번의 실험만으로 누수나 특정 지연 원인을 확정하지 않는다. 미전송 때문에 최종 고유 명령 수와 체결 수가 소폭 달라 정확히 같은 최종 상태 크기의 비교도 아니다. WAL 크기는 배치 구성에도 영향을 받는다.

## 정상 재시작과 복구 검증

부하 종료 후 서버가 살아 있는 동안 최초 결과·현재 주문·잔고·호가·전체 체결을 GET으로 보존했다. 정상 종료 뒤 같은 바이너리와 run을 열고 전체 조회를 다시 수행했다. 최초 결과 GET 검증을 마친 뒤에만 기존 명령 12개를 POST 재시도하고 전체 상태를 다시 비교했다.

| 검증 | 스냅샷 끔 | 스냅샷 켬 |
| --- | ---: | ---: |
| 고유 명령 최초 결과 | 51,373개 일치 | 51,385개 일치 |
| 현재 주문 | 45,270개 일치 | 45,280개 일치 |
| 체결 | 12,114개 일치 | 12,117개 일치 |
| 계정 | 4개 잔고·자산별 전체 공급량 일치 | 4개 잔고·자산별 전체 공급량 일치 |
| 선택된 스냅샷 순번 | 없음 | 51,385 |
| 추가 WAL 명령 재생 | 51,373 | 0 |
| process 시작→ready 및 health 성공 | 1.223초 | 4.713초 |
| 재시도 후 전체 조회·WAL hash | 변경 없음 | 변경 없음 |
| 최종 소유 서버 종료·포트 해제 | 확인 | 확인 |

전체 조회 파일의 SHA-256은 종료 전·복구 후·재시도 후 각각 동일했다. 각 최초 결과는 loadgen이 실제 응답에서 계산한 원래 SHA-256과도 대조했다. 응답받은 모든 고유 명령을 검사했으며 복구 검증은 표본 추출이 아니다. 중복 POST 자체만 12개를 선택했다.

이번에는 스냅샷 복구가 약 3.85배 오래 걸렸다. 현재 구현은 checkpoint JSON 읽기·구조 및 관계 검증뿐 아니라 보존된 WAL 전체와 입력/순번 일치 검사를 수행한다. 따라서 추가 명령 재생이 0이어도 전체 기동 비용이 사라지지 않는다. 이 처리 구조는 원인 후보지만 단계별 프로파일 없이 어느 단계가 차이를 만들었다고 확정하지 않는다. 기동 시간은 각 1회이며 OS 파일 캐시를 비우지 않았다. 10ms 주기의 ready 확인과 health 조회가 포함된다.

켬 조건은 부하 뒤 전체 조회 중에도 주기 스냅샷을 생성했다. 그 결과 최종 명령까지 포함한 스냅샷을 선택했다. 이 결과는 WAL suffix가 긴 복구나 비정상 종료·전원 장애 검증을 대신하지 않는다.

## 원본·재집계와 재현

[전체 기계 판독 결과](20261030-soak-comparison.json)에 원본 재집계, 모든 5초/60초 구간, 환경·바이너리/입력 hash, 전체 복구 결과와 근거 파일 hash를 보존했다. [원본 보관 정보](20261030-soak-artifacts.json)에 파일 수·전체 크기·manifest hash를 기록했다.

원본은 Git 제외 `var/soak-comparison-20261030.92490s/`에 약 3.51GiB로 보존한다. 서버/생성기 바이너리, 초기 설정, 입력 계획·응답 표본, 계측, 실제 run, 전체 HTTP 조회, 실행/분석 스크립트를 포함한다. Git에는 보고서·요약 JSON·설정만 들어가므로 clone만으로 전체 원본과 실험 스크립트를 얻을 수는 없다. 기존 데이터나 이번 원본은 삭제하지 않았다.

실행 전 6초 스냅샷 예비 실행으로 실제 프로세스·전체 조회·재시작·중복 재시도를 검증했다. 별도 검사에서 잘못된 잔고·순번·최초 결과 바이트와 변조된 원본 해시를 거절했다. Go의 기존 bench.Summarize/SummarizeWindows로 저장된 요약과 전체 표본을 재대조했고, Python의 독립 계산으로 두 조건의 전체/모든 120개 5초 구간/10개 1분 구간의 p99·누락 수를 확인했다.

정상 완료 marker가 없는 끔 조건도 분석하도록 오프라인 분석기를 보완했다. 변경 전 분석기 원본을 보존하고 현재 분석기 hash를 결과 JSON에 별도로 기록했다. 이 보완은 요청 누락 실패를 성공으로 변경하지 않는다. 비교용 서버·생성기·runner·입력은 두 조건에서 동일하다.

원본 묶음이 있는 경우 기존 run을 건드리지 않고 새 parent에 같은 bin 사본을 준비한 뒤 아래 명령을 사용한다. `NEW_ROOT`는 아직 normal/snapshot 하위 폴더가 없는 새 parent다.

```sh
python3 var/soak-comparison-20261030.92490s/run.py --root NEW_ROOT --scenario normal --workload config/benchmarks/soak-10m-v1.json --config config/benchmarks/config-v1.json
python3 var/soak-comparison-20261030.92490s/run.py --root NEW_ROOT --scenario snapshot --workload config/benchmarks/soak-10m-v1.json --config config/benchmarks/config-v1.json
```

다음 성능 작업은 같은 상태 크기에서 snapshot capture/게시와 복구 검증 단계의 비용을 각각 계측하고, 생성기 지연 원인도 분리하는 것이 적절하다. 새 후보의 채택은 별도 반복 비교로 판단한다. 이번 요청은 측정·복구·결과 비교까지 완료했으며 실제 전원 장애 검증은 계속 보류한다.
