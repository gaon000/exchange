# P7 스냅샷 정렬 이동과 비교

상태: 비교·채택 판정 완료 — 두 후보 모두 기준 미달로 미채택, P6 구현 복원. v1 전체 계획과 필수 미완료 검증은 계속 유지한다.
작성일: 2026-10-29 (Asia/Seoul).

## 선택 근거

[P6 기준 측정](p6-baseline.md)에서 정상 29,000 requests/s는 세 번 통과했지만 snapshot을 켠 같은 부하는 세 번 모두 지연·생성기 누락으로 탈락했다. owner의 상태 복사·정렬 최대는 656.942~706.851ms였고 진단 profile의 Engine.Capture 누적 CPU 표본 1.00초 중 sort.Slice가 0.69초였다. 명령을 처리하지 못하는 구간에서 정렬을 분리하는 것을 첫 개선으로 선택했다.

## 실험한 한 가지 변경

후보 `a124885`와 `798f3b3`의 CopyCheckpoint는 명령 경계에서 가변 상태를 분리 복사했다. 아래는 실험 당시의 구조이며 현재 [checkpoint 구현](../../internal/engine/checkpoint.go)은 P6 기준으로 복원했다. runtime은 복사본의 소유권을 기존 snapshot worker에 넘기고 다음 주문·조회를 처리한다. worker가 계정·주문·최초 결과 배열을 기존 기준으로 정렬한 뒤 파일을 게시한다. FIFO·체결 순서는 그대로 복사한다. 동기 Capture의 반환 순서, 저장 bytes, 복구 검증, WAL sync·성공 응답 순서와 동시 사본 한 개 제한은 유지한다.

현재 복원된 계약은 [저장 설계](../design-docs/storage-v1.md#5-snapshot-dto와-게시)가 소유한다. 외부 의존성·새 worker·새 실행 옵션은 추가하지 않았다. 아직 복사 자체의 할당·GC나 snapshot 직렬화를 최적화하지 않았다.

실험 후보의 snapshotCapture 계측은 owner의 복사만 포함하고, 정렬 비용은 snapshotPublish의 worker 구간으로 이동한다. capture 시간 감소만으로 전체 CPU/게시 비용이나 p99가 줄었다고 판단하지 않는다. 두 구간·전체 요청 지연·누락·메모리를 함께 비교한다. P6 원본의 capture는 복사와 정렬을 모두 포함한다.

## 후보의 회귀 검증

- 독립 golden checkpoint JSON과 snapshot envelope, 손상된 순서 거절·저장/복구 테스트를 유지했다. CopyCheckpoint를 나중에 정렬한 결과도 golden bytes와 일치했다.
- 복사 이후 실시간 체결·취소가 진행돼도 사본의 상태/최초 결과/FIFO가 원래 경계로 복구됨을 확인했다. Restore는 저장 파일의 비정규 순서를 정렬해 수리하지 않는다.
- 테스트 hook으로 worker를 정렬 직전에 멈춘 상태에서 주문·조회 완료, 두 번째 snapshot 거절, Shutdown 대기와 저장소 잠금 유지, 정렬 재개 후 과거 경계 게시를 확인했다.
- worker 정렬 경계의 panic을 주입했을 때 게시·순번 전진 없이 INTERNAL_FAILURE로 중단하고 저장소를 닫았다. 파일 게시·복구·HTTP 장애/프로세스 종료 검증도 전체 race 실행에 포함했다.
- `scripts/go test ./... -timeout=180s`, `scripts/go test -race ./... -timeout=180s`, `CGO_ENABLED=0 scripts/go test ./internal/engine ./internal/runtime ./internal/snapshot -timeout=120s`, 전체 vet/build가 통과했다. cgo 비활성 검사는 실제 APFS 검증을 대신하지 않는다.

[고정 조건 v1](p6-baseline.md#고정-비교-조건-v1)의 입력·기간·20ms·오류/누락·반복 기준을 유지했다. 첫 후보 서버는 clean commit `a124885a89883c7f199118e87ed0bfc40058654b`이고, 생성기·실행기·판정 도구는 P6의 `58836215ccbdf5171ac351d6b633b692366e0a17` 바이너리로 고정했다. 기준 서버 대조도 같은 P6 바이너리를 사용했다. 모든 실행은 새 run이며 원본과 실패 결과를 유지했다.

후보 17회와 기준 대조 5회, 총 22회다. 25,000/s의 여섯 실행은 각 실행 전 동일한 30초 유휴 시간을 두고 후보→기준→기준→후보→후보→기준 순서로 수행했다. 원본 기록/재집계 직후 다음 실험을 시작하는 순서 효과를 줄이기 위한 추가 대조이며, 앞선 실행을 제외하거나 20ms를 완화한 것이 아니다. 각 묶음의 시각과 `paired-25000-protocol.json`에 순서를 남겼다.

snapshot 29,000의 owner 복사 최대는 P6의 656.942~706.851ms에서 첫 후보의 153.756~272.281ms로 줄었다. 그러나 요청 p99는 104.954~125.140ms, 생성기 누락은 21,252~66,600개로 여전히 기준 밖이었다. worker 정렬·게시 최대는 8.090~13.493초였고 peak RSS는 1,846~1,978MiB였다. capture 시점의 상태 크기·게시 횟수와 서버 생애 관찰 범위가 다르므로 이 범위의 비율을 통제된 개선률로 해석하지 않는다.

진단 profile은 CopyCheckpoint 누적 CPU 표본 0.40초가 owner에, CanonicalizeCheckpoint 1.31초가 별도 worker에 있음을 확인했다. 정렬 비용을 제거한 것이 아니라 위치를 옮긴 결과다. 전체 요청 지연이나 기준 지속 처리량 향상은 입증하지 못했다.

일부 normal 실행의 WAL sync 최대가 40ms 이상이었으며, 실험 사이 단일 프로세스 관찰에서는 시스템 색인 프로세스 mds_stores가 CPU 98.6%를 사용했다. 이는 각 측정 창의 시스템 추적이 아니며 실패 원인으로 확정할 수 없다. 기존 서버의 대조도 일부 실패했으므로 코드 회귀·외부 자원 경쟁을 구분할 근거가 부족하다. 시스템 서비스를 종료하거나 전역 색인 설정을 바꾸지 않았다.

[원본 재검증 결과](20261029-p7-snapshot-sorting-initial.json)와 [profile 해석](20261029-p7-initial-profiles.txt)에 모든 결과를 남긴다. 원본 생성 경로는 Git 제외 `var/p7-snapshot-sorting-kyynt605/`, 기준 대조는 그 안의 `baseline-controls/`다. 비교 종료 후 아래 압축본으로 보관했다. 원래 P6 raw는 [검증한 압축본](20261029-p6-archive.json)으로 보관했으며, 같은 bytes의 기준 실행 파일은 P7 parent의 reference-bin/에도 복사해 보존했다. 부족해진 공간은 재생성 가능한 프로젝트 Go 빌드 캐시 정리와 검증된 P6 압축 보관으로 확보했다. 실험 원본을 버리지 않았다.

## 사전에 정한 최종 후보와 채택 기준

첫 후보는 테스트용 beforeSnapshotSort 함수를 Runtime.hooks에 추가해 정상 경로의 구조 배치까지 바꿨다. 이 부수적인 차이를 줄이기 위해 테스트 저장 어댑터의 선택적인 내부 hook으로 이동했다. Runtime과 owner 정의는 P6 기준과 같아지고, 정렬 자체는 기존 snapshot worker에 남는다. 이 변경이 지연 변동의 원인이라는 주장은 하지 않는다.

실행 전에 다음 조건을 정했다. 최종 후보는 clean 서버와 고정된 기존 생성기/도구로 정상 29,000/s를 세 번 확인한다. 모두 통과하면 snapshot 29,000/s 세 번과 별도 profile로 비교한다. 정상 기준을 재현하지 못하면 이 성능 후보를 채택하지 않고 기준 구현을 유지한다. 새 임계값을 유리하게 선택하거나 불리한 반복을 제외하지 않는다. 최종 판정과 소스 revision·원본 위치는 아래에 기록했다.

실제 전원 장애는 별도 장비가 없어 계속 미완료이며 전체 계획의 완료 조건은 유지한다.

**결정: 정렬 이동 후보를 채택하지 않고 P6 소스 구현을 유지한다.** 정상 조건을 세 번 재현해야 하는 선행 조건에 미달했으므로 최종 후보의 추가 snapshot/profile 실행은 하지 않았다. 앞선 후보의 snapshot/profile 결과는 별도로 보존한다. 후보 변경과 전용 테스트는 Git 이력에 남기고, 현재 engine/runtime 소스·계측 의미는 P6로 복원했다. capture에는 복사와 정렬, publish에는 파일 게시가 포함된다. 저장 bytes·공개 API·거래/내구성 계약은 바뀌지 않았다.

P6의 정상 29,000 requests/s에서 3회 통과한 결과는 당시 조건의 측정 기록이다. 이후 기존 서버 대조도 일부 탈락했으므로 지금의 호스트에서 항상 재현되는 성능 보장이나 후보의 확정적 코드 회귀로 주장하지 않는다. 이번 실험에서 owner 정렬 비용을 옮겼다는 근거는 확보했지만 전체 경로의 성능 개선은 입증하지 못했다.

## 원본 보관과 복원

두 P7 디렉터리의 모든 일반 파일·디렉터리를 압축본과 대조했다. 861개 항목의 종류·권한·크기와 각 파일 SHA-256이 일치했고, 압축 중 원본 경로·inode·크기·수정 시각이 바뀌지 않았음을 확인한 뒤 비압축 사본만 제거했다. 약 24.96GB의 원본 내용이 2.74GB의 압축 파일에 보존되며, 실패 실행·WAL·snapshot·바이너리·profile·입력/표본·사전 protocol·재집계 스크립트도 포함한다. 각 멤버의 검증 receipt와 압축본은 Git 제외 `var/archives/`에 있다.

| 묶음 | 압축 경로 | 검증 항목 수 | 보관 메타데이터 |
| --- | --- | --- | --- |
| 첫 후보/기준 대조 22회 | `var/archives/p7-snapshot-sorting-kyynt605.tar.gz` | 756 | [해시·receipt](20261029-p7-initial-archive.json) |
| 최종 후보 3회 | `var/archives/p7-final-pqepq5wq.tar.gz` | 105 | [해시·receipt](20261029-p7-final-archive.json) |

복원 전 메타데이터의 SHA-256을 확인하고, 대상 디렉터리가 없는지와 원본 용량만큼 여유 공간이 있는지 확인한다. 저장소 루트에서 아래 명령으로 원래 경로를 복원할 수 있다. 두 번째 묶음의 재집계 스크립트는 첫 번째 묶음의 reference-bin을 사용한다.

```sh
tar -xzf var/archives/p7-snapshot-sorting-kyynt605.tar.gz -C var
tar -xzf var/archives/p7-final-pqepq5wq.tar.gz -C var
```

JSON 요약·해시·보고서는 Git에 포함하지만 큰 원본 압축본은 로컬 보관이다. 저장소 clone만으로 원본 표본을 얻을 수는 없다. 이 보관 검증은 실제 전원 장애 내구성 시험이 아니다.

## 남은 검증과 재개 조건

- 스냅샷을 켠 29,000 requests/s는 P6와 첫 후보 모두 기준 미달이다. 후속 [스냅샷 한계 측정](p7-snapshot-capacity.md)에서는 기준 구현의 요청률만 탐색해 3,000/s 세 번 통과·4,000/s 실패를 확인했다. 기존 실패나 20ms 기준을 삭제·완화하지 않았으며 29,000/s의 스냅샷 통과나 코드 성능 개선을 주장하지 않는다.
- 현재 자료만으로 추가 소스 변경을 성능 개선으로 채택하지 않는다. 새로운 후보에는 별도 가설·사전 비교 조건·전체 회귀 검증이 필요하다.
- 실제 전원 장애는 사용자 확인대로 별도 장비가 없어 미완료다. APFS 호출/프로세스 kill 검증은 이를 대신하지 않는다. P7 전체 완료 조건과 v1 실행 계획은 Completed로 바꾸지 않는다.
