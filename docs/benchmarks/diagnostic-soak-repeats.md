# 진단 계측을 켠 스냅샷 유무 10분 반복 비교

2026-11-03, clean `74a1206af94ada42eabbc5440e651c779bf181e5`의 바이너리로 스냅샷 끔/켬을 각각 600초 3회 실행했다. **여섯 실행 모두 전체 재시작·복구 검증은 일치했다. 미전송은 scheduler 검사 8건·worker 검사 7건으로 구분됐고, 켬 조건은 세 번 모두 5초 구간별 지연 초과가 남았다.** 생성기 실행 지연과 서버 저장 지연이 함께 관찰되며 단일 원인은 확정하지 않았다.

scheduler는 전달 전 관찰 시점에 이미 50ms를 초과한 경우다. worker는 전달 전 검사에서는 한도 안이었으나 worker 첫 실행에서 초과한 경우다. 예를 들어 켬 2의 152.00초 요청은 scheduler 관찰까지 34.531ms, 그 관찰부터 worker까지 39.862ms가 걸렸다. 이 두 번째 값은 CPU 실행 시간이나 내부 대기열 길이를 의미하지 않는다.

미전송 15건을 포함하는 생성기 계측 구간에는 모두 GC 횟수 증가가 0이었다. 해당 서버 계측 구간의 GC 증가도 모두 0이었다. 따라서 관측한 GC 증가만으로 이 사례를 설명할 수 없다. 샘플링 밖의 스케줄링, 호스트 자원 경쟁과 다른 지연은 배제하지 않는다. 생성기 주기 표본의 skippedIntervals는 여섯 실행 모두 0이며, 이것이 개별 요청의 발사 지연이 없었다는 뜻은 아니다.

UTC 대조상 15건 모두 관찰 시각에 snapshot 호출과 겹치지 않았다. 이는 snapshot의 지속적인 CPU/메모리 부담이나 앞선 작업의 간접 영향을 배제하지 않는다. 특히 절대 시각 정렬에는 아래 오차가 있어 짧은 사건의 인과관계를 확정할 수 없다.

## 검증·보관·해석

6초 예비 실행에서 실제 HTTP/APFS·전체 복구를 확인했다. 검증기의 잔고/순번/최초 결과 오류 검출과 원본 hash 변조 거절 2개 테스트, completion hash를 다시 계산한 dispatch/process 변조 거절 2건도 통과했다. 각 본 실행에서 Go의 Summarize·SummarizeWindows와 진단 의미 검증을 수행했다. 별도 Python 계산으로 warmup/measurement 12개 전체 요약, 720개 5초·60개 1분 구간의 예정/실행/미전송·분위수를 대조했고, 각 서버 단계 histogram의 구간 차분 합계가 전체 차분과 일치했다.

서버·생성기 자원은 약 500ms 표본이며 요청과 동일 cohort가 아니다. client monotonic offset과 서버 UTC를 대조했다. UTC 경과−monotonic 경과의 종료 시 차이는 실행 순서대로 -0.822/-0.801/+29.831/+4.881/+4.880/-14.480ms다. 끝점 차이는 실행 중 모든 시점의 오차 상한이 아니다. GC CPU와 GC pause는 다른 지표이며 구간별 중첩을 인과 증명으로 쓰지 않는다.

원본 parent에는 고정 binary·입력·환경·protocol·harness, loadgen 여덟 원본, 계측, 전체 복구 결과, snapshot/조회 archive와 member manifest를 보존한다. 여섯 archive의 모든 member를 사후 다시 대조했다. Git에는 본 보고서와 선택 집계 JSON만 기록한다. 실행 명령은 `python3 -u var/diagnostic-soak-20261103.fz83p2f4/run_suite.py`, 분석은 같은 parent의 `analyze_suite.py`, `build_report.py` 순서다. 분석 출력이 있으면 bytes 일치를 검사하며 재실험은 새 parent가 필요하다.

이번 작업의 추적 변경은 문서·집계 자료이며 production source 변경은 없다. 원본 재검증·실험 도구·문서 검증을 수행했다. 2026-11-03 실험 완료 당시에는 커밋·병합·push 및 새 GitHub CI 실행을 하지 않았다.

다음 진단은 **별도 trace 실행에서 생성기 scheduler/worker 지연을 재현하고, 같은 시각의 호스트 CPU·I/O와 서버 저장 경계를 함께 확인하는 것**이 적절하다. 서버 저장 지연과 snapshot이 켜진 상태의 지연 초과도 따로 추적한다. 이번 결과만으로 특정 엔진 최적화를 선택하거나 계측을 끈 실행의 성능 향상을 주장하지 않는다.
