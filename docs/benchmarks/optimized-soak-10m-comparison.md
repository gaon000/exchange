# 최적화 버전의 스냅샷 유무 10분 부하·복구 비교

2026-11-02, clean `e5fb8603ec8166fbe78409f114fd59bae6b4ca32`로 스냅샷 끔/켬을 각각 10분 실행했다. **두 조건 모두 전체 상태·최초 결과·중복 재시도 복구는 통과했다. 스냅샷 켬의 CPU·평균 생성 시간·복구 시간은 줄었지만, 전체 요청 p99는 두 조건 모두 이전보다 높았다.** 켬 조건에는 생성기 미전송 9건도 있어 유효한 성능 측정으로 판정되지 않았다. 두 조건 모두 누락 0과 5초 구간별 p99 20ms 참조 기준을 함께 만족하지 못했다.

[이전 10분 보고서](soak-10m-snapshot-comparison.md), [전체 기계 판독 비교](20261102-optimized-soak-comparison.json), [원본 보관 정보](20261102-optimized-soak-artifacts.json)를 함께 읽는다. 이전 결과는 `3b5a6f5` 기준이며 이번 버전은 단계 계측·복구 decoder·생성 크기 사전 계산 개선을 모두 포함한다. 특정 변경 하나의 인과 효과로 해석하지 않는다.

현재 켬의 CPU는 18.8%, GC CPU는 24.0%, snapshot 평균 시간은 16.8% 감소했다. 반면 peak RSS는 1.5%, snapshot 시간 p99는 4.7% 증가했다. 모든 자원 지표가 줄었다고 보고하지 않는다. 전체/후반 지연 개선을 보장하지 않는다는 결과는 [동일 고정 상태 5쌍 비교](snapshot-preflight-optimization.md)의 적용 범위와 일치한다.

snapshot 시간은 측정과 겹친 120개 event 각각의 전체 호출 시간이다. 상태가 커지는 서로 다른 크기이며 마지막 상태만 5회 반복한 이전 미시 비교와 분모가 다르다. 저장·snapshot 오류는 두 현재 조건 모두 0이고 켬 event 120개 모두 COMPLETED였다. 종료 전 전체 조회 중에도 주기 snapshot이 동작해 최종 파일이 122개 남았다.

CPU·GC 증분은 측정 시작/끝 직전 계측을 사용한다. 실제 관측 간격은 이전 끔/켬 600.001/600.456초, 현재 끔/켬 599.990/600.001초다. peak RSS는 워밍업을 포함한 프로세스 생애 최대값이며 live heap은 최근 GC 기준이다. 부하 후 전체 조회·재시작 비용은 이 자원 표에서 제외했다.

새 단계 계측에서는 완료 단계당 평균이 capture.copy 21.570ms, capture.sort 18.964ms, publish.measure 29.612ms, publish.encodeWrite 247.643ms였다. 실제 인코딩/쓰기가 여전히 큰 비용이다. 각 단계는 500ms 계측 경계 사이 count/sum 증가분으로 계산하며, 경계에서 진행 중인 작업 때문에 완료 건수가 다를 수 있다. 정확히 같은 120개 event의 분해로 합산하지 않는다. 이전 10분 실행에는 해당 세부 계측이 없어 동일 단계의 직접 전후 비교는 할 수 없다.

켬의 준비 시간은 46.9% 감소했지만 현재도 끔보다 약 2.18배 길다. snapshotSeq 뒤 추가 재생은 0이어도 보존된 WAL 전체 대조와 의미 검증은 유지된다. 각 재시작 1회·캐시 미초기화·최종 상태 크기 차이·10ms 주기 ready 확인과 health 요청이 포함된 관찰값이다. 비정상 종료나 실제 전원 장애 검증으로 해석하지 않는다.

## 검증·재현과 해석

6초 예비 실행의 snapshot·전체 복구·재시도와 검증기 오류 검출 2개를 먼저 통과했다. 현재 및 이전의 네 실행을 현행 Go `bench.Summarize/SummarizeWindows`로 재계산해 저장 요약과 일치했고, 이전 분석 JSON도 그대로 재현됐다. Python 별도 계산으로 각 60,500개 표본과 워밍업/전체 측정 분위수, 120개 5초·10개 1분 구간의 분위수·미전송·오류 수를 대조했다. 전체 HTTP 조회/WAL hash와 runId 제외 계획의 일치도 재검증했다.

원본은 Git 제외 `var/soak-optimized-20261102.yawwm75d`에 보존한다. 기존 234개 원본도 hash를 대조했고 변경하지 않았다. 원본에는 binary/build info, 동일 입력·환경/protocol, run과 모든 snapshot, 계획·응답 표본·계측·전체 조회, 검증 결과·분석 소스가 있다. Git에는 보고서·집계 JSON·manifest 요약만 들어가며 원본 업로드는 하지 않았다.

실행 명령은 `python3 -u var/soak-optimized-20261102.yawwm75d/run_suite.py`였다. 순차 실행과 30초 유휴만 관리하며 원본의 run.py는 그대로다. 재집계는 `bin/analyze <case>/loadgen <새 분석 JSON>`을 현재/이전 각각 수행한 뒤 새 원본의 `compare.py`, `verify_compare.py`, `supplement.py` 순으로 실행했다. 재실험은 새 고유 parent에 같은 harness와 검증한 bin 사본·입력을 준비하고 source/environment/hash 정보를 갱신한다. 기존 case·결과 파일 재사용을 거절한다.

이번 작업에서 production source·dependency·설정은 변경하지 않았다. 동일 commit의 기존 CI를 반복 실행하지 않았고 실험 도구 검증·원본 재집계·문서 검증을 수행했다. 커밋·병합·push는 하지 않았다. 실제 전원 장애 검증은 계속 보류한다.

다음 성능 작업은 최적화 추가보다 생성기 발사 지연과 서버 응답 지연을 분리해 관찰하는 것이 우선이다. 5분·7분 구간의 미전송, 9분 끔 조건의 지연도 있으므로 snapshot만 원인으로 단정할 수 없다. 호스트 상태를 기록한 반복 교대 실행과 필요한 구간의 별도 trace로 원인을 좁히는 것이 적절하다. 이 보고서는 추가 최적화나 해당 후속 실험을 수행했다고 주장하지 않는다.
