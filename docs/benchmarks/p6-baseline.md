# P6 전체 경로 측정 기준과 결과

상태: Completed (P6 기준 측정) — 정상 조건의 반복 기준 확정, 스냅샷 조건의 목표 미달과 프로파일 근거 기록. P7 개선·최종 비교와 실제 전원 장애 검증은 미완료.
기준 고정일: 2026-10-29 (Asia/Seoul).

## 범위와 근거

공개 HTTP 요청부터 APFS의 F_FULLFSYNC·순차 적용·전체 응답까지를 측정한다. [측정 계약](../design-docs/benchmark-v1.md)의 시간·분모·중복·오류 정의를 사용한다. 이 문서는 P6의 초기 실측, 고정 기준, 반복 baseline을 소유한다. P7에서 결과를 본 뒤 기준을 유리하게 바꾸지 않는다. 초기 탐색 수치와 아래 고정 조건의 baseline은 다르다.

## 초기 탐색

소스 `cb47f918216dea9d1f72cf6a68dc70a35b83d5b3`, modified=false인 바이너리를 사용했다. Go 1.27.3, Apple M3 Pro·18 GiB RAM, macOS 15.8 (24H23), 로컬 APFS·4,096-byte block이며 AC 전원 연결을 확인했다. 동일 개발 컴퓨터에서 서버와 생성기를 함께 실행했다. 다른 앱의 자원 사용·열 상태를 완전히 통제한 전용 벤치마크 장비는 아니다.

각 rate에서 새 run, seed=17, 거래 계정 3개와 무잔고 거절 계정, 양쪽 10 level, 주문 수량 1 lot, Rest/Marketable/Cancel/Duplicate/RejectProbe=35/30/10/15/10을 사용했다. 워밍업 2초·측정 10초, 생성기 동시 한도 2,048·발사 지연 한도 50ms·요청 deadline 5초, 서버 기본 배치/큐, 500ms 계측이었다. snapshot과 profiler는 껐다. 아래 p99는 측정 cohort이며 예정 p99는 고유 신규 승인 주문의 원래 예정 시각부터 성공 관찰까지다.

원본은 Git 제외 경로 `var/p6-initial-dgzi6jmf/`에 있다. 각 normal-RATE 디렉터리는 바이너리·설정·raw 표본·서버 계측을 포함한다. 유효한 일곱 실행에는 completed.json과 해시가 있고, 70,000/s에는 failed.json이 있다. parent의 overview.json은 편의 집계이며 원본의 대체물이 아니다. 최초 편의 집계에서 peakRssBytes 필드명의 대소문자 오류로 스크립트가 멈췄지만 100/s 실험은 이미 정상 완료됐다. 해당 실험을 다시 실행하지 않고 필드명 수정 후 남은 rate만 이어갔다.

20ms는 초기 탐색의 저·중부하 p99 약 7~10ms에 여유를 두면서, 70,000/s에서 나타난 수십 ms의 대기와 생성기 누락을 정상으로 인정하지 않도록 정한 실험 기준이다. 서비스 SLA나 사용자가 요구한 모든 요청의 최대 지연 보장이 아니다.

100만 예정 시도 상한으로는 5+20초에서 40,000/s까지만 측정할 수 있었다. 초기 탐색에서 그 이상의 범위를 확인할 필요가 있어 생성기의 유한 상한을 200만으로 늘렸다. rate 상한 100만/s·전체 시간 1시간, snapshot 2 GiB 파일 한도와 거래 규칙은 유지한다. 이 조건에서는 최대 80,000/s까지 같은 기간으로 요청할 수 있다. 초기 config의 maxCommands도 200만이며 실제 고유 명령 수는 중복을 제외해 그보다 작다. 메모리·파일 비용은 늘어나므로 그 영향을 숨기지 않는다. 아직 200만 시도 전체의 실행 성능을 검증했다는 의미는 아니다.

## 원본 재검증과 판정 도구

[benchreport](../../tools/benchreport/main.go)는 실행이 끝난 묶음을 오프라인으로 읽는다. 서버나 부하 생성기를 시작하지 않으며 측정과 동시에 실행하지 않는다. 최대 100개 묶음을 받아 서로 다른 조건을 같은 반복으로 합치지 않고 JSON 보고서를 만든다. 보고서는 기존 실험 디렉터리 밖의 새 파일만 허용한다. 디렉터리 alias도 해석해 원본 묶음 안에 보고서를 쓰거나 같은 경로를 중복 입력하는 것을 거절한다.

- completed.json의 모든 파일 해시와 파일 집합을 확인한다. 누락·미기재 파일·symlink/특수 파일·변조는 evidence 오류다. loadgen의 6개 해시·plan digest·run/config identity도 다시 대조한다.
- 설정·seed·runId로 Plan을 재구성하고 plan.jsonl의 모든 요청을 비교한다. 전체 samples.jsonl을 [Summarize](../../internal/bench/summary.go)로 다시 계산해 저장된 summary와 일치해야 한다. 새 집계가 틀릴 가능성은 독립 기대값의 단위 시험으로 별도 확인하며 재집계만으로 매칭 정확성까지 증명한다고 주장하지 않는다.
- 전체 지연/오류와 [구간 집계](../../internal/bench/windows.go)를 판정한다. 창은 예정 시각으로 나누며, 응답이 다음 창이나 drain까지 늦어져도 원래 창에 남긴다. 서버 계측의 startedUTC를 같은 창에 대응시키고 최소 관찰 수·큐 평균 증가를 검사한다.
- 고정 workload/config·계측 주기·snapshot/profile 설정·관찰 환경과 바이너리 revision을 검사한다. revision 미상/modified 빌드는 채택하지 않는다. snapshot 완료 이벤트와 실제 측정의 교집합을 다시 세고 profile 시각·압축 무결성을 확인한다.
- source/binary·config·workload(rate 제외)·runtime/HTTP 설정·시나리오·관찰 하드웨어/환경별 series를 만든 뒤 rate별 반복을 모은다. 모든 포함 실행이 통과하고 서로 다른 runId가 3개 이상이어야 qualified=true다. 복사한 run은 양쪽 모두 중복으로 탈락하며, 실패한 반복도 같은 그룹의 runs에 남는다.

출력의 cases는 원본 경로, sealed/summaryRecomputed/pass/reasons, 전체 summary·창별 분포/큐·snapshot 교집합과 프로세스 누적 CPU/peak RSS·WAL 크기를 포함한다. snapshotCapture/Publish 누적 시간도 서버 생애 관찰이며 측정 구간만의 비용이 아니다. groups는 실제 반복 수·통과 수·qualified와 고유 신규 주문/s 범위·최악 p99를 담는다. 보고서 자신의 build 정보와 기준/참조 입력의 SHA-256도 기록한다.

완료 표식이 없는 실패 실험도 가능한 원본을 재집계하지만 UNSEALED_EXPERIMENT로 탈락한다. 다른 증거 오류나 일부 파일 부재는 cases.reasons에 남기며 누락된 수치를 성공 실적으로 사용하지 않는다. 명령 종료 코드 0은 보고서를 기록했다는 의미이며 성능 통과는 cases.pass/groups.qualified를 확인해야 한다. 전달하지 않은 실험까지 발견해 검증하지는 못하므로 trial 목록과 모든 실패 실행을 함께 보존하고 입력한다. 환경/바이너리 해시는 재현 자료이며 서명된 제3자 검증은 아니다.

## 반복 baseline 결과

소스 `58836215ccbdf5171ac351d6b633b692366e0a17`, modified=false인 서버·생성기·판정 도구로 14개 독립 run을 실행했다. 위 고정 조건을 그대로 사용했고 각 실행의 환경은 초기 탐색과 같은 장비·OS·Go·APFS였다. 초기 탐색의 2+10초와 이번 5+20초는 다른 조건이므로 결과를 합치지 않는다.

### 채택점의 지연·거래·자원

정상 29,000/s의 측정 예정/시작 수는 매회 580,000개였다. 요청 p50은 3.762~3.981ms, p95는 7.052~8.015ms, p99는 10.299~12.043ms, 관찰 최대는 24.245~26.814ms였다. p99 목표가 모든 요청의 최대 지연 보장은 아님을 이 값에도 적용한다. 성공 취소는 579.50~581.25/s, 체결은 5,788.00~5,795.45/s였다. 같은 입력 계획이어도 동시 HTTP 도착 순서는 달라져 체결/취소의 실제 결과 수는 달라질 수 있다.

준비·워밍업·측정·drain을 포함해 매회 616,402개 고유 명령을 적용했고, 완료 응답에서 집계한 생성 주문은 준비 20개를 포함해 544,048개, 체결은 144,611~144,846개였다. WAL은 136,249,383~136,265,555bytes였다. 서버 생애 CPU는 45.70~46.16 CPU초, peak RSS는 1,266~1,303MiB, 마지막 Go live heap은 679~694MiB, GC 누적 CPU는 12.32~13.54초였다. 이력·최초 결과를 유지하는 조건의 메모리 비용이다.

생성기의 Run 전후 CPU 차이는 46.80~48.17 CPU초, Run 후 생애 peak RSS는 1,065~1,089MiB였다. 서버와 생성기는 같은 장비를 공유한다. CPU 누적 값은 여러 코어의 합이며 서버 생애와 생성기 Run 관찰의 범위도 서로 다르다. peak RSS는 측정 구간의 현재 RSS나 두 프로세스의 동시 합계가 아니다.

### 스냅샷과 프로파일의 영향

profile만 켠 세 실행도 같은 부하에서 통과했다. 정상 결과와 별도 series로 유지하며, 이 표본만으로 프로파일 비용이 없거나 성능이 개선됐다고 해석하지 않는다. CPU 수집은 준비부터 종료까지이고 종료 heap/allocs에는 강제 GC가 포함된다.

snapshot 세 실행은 각각 측정과 겹친 완료 이벤트가 2개였지만 모두 지연·생성기 누락 기준에 실패했다. 각 실행의 상태 복사 최대는 656.942/706.851/679.549ms, 게시 최대는 7.592/8.080/8.873초였다. 서버 peak RSS는 1,911~1,974MiB로 정상 실행보다 컸다. snapshot 주기는 서버 시작 기준이므로 부하 준비 시간에 따라 복사 시점의 누적 상태 크기가 달라진다. worker는 밀린 주기를 건너뛰며, 종료 중 대기 취소로 남은 UNKNOWN 이벤트는 실제 게시 실패나 파일 부재를 뜻하지 않는다. 게시 worker의 종료 합류·최종 파일·계측은 원본에 남아 있다.

snapshot-profile 진단 실행에서도 지연·누락이 발생했다. [pprof 출력](20261029-p6-profiles.txt)의 capture 필터에서 Engine.Capture 누적 CPU 표본 1.00초 중 sort.Slice가 0.69초였다. P6 측정 버전의 [Capture](../../internal/engine/checkpoint.go)는 명령을 변경하는 owner 안에서 분리 사본을 만들고 주문/결과를 정렬한다. 정렬은 복사 경로의 확인된 비용이며, 이를 사본만 소유하는 worker로 옮기는 것을 P7의 첫 비교 후보로 정했다. 복사 자체의 메모리 할당, GC와 게시 직렬화 비용은 여전히 남으므로 목표 달성을 미리 주장하지 않는다.

normal profile 첫 실행의 표본 할당은 약 8,685MiB, 종료 in-use 표본은 약 683MiB였고 GC 경로와 WAL 인코딩·엔진 이력 유지 비용도 관찰됐다. 이 결과는 추가 후보이며 여러 개선을 동시에 섞지 않는다. 프로파일의 시스템 호출 표본 비중만으로 저장 장치가 유일한 병목이라고 결론내리지 않는다.

## 원본·재현·후속 비교

[기계 판독 결과](20261029-p6-baseline.json)는 14개 실행 전체를 다시 읽은 benchreport, 모든 trial의 성공/실패, 서버 최종 계측·생성기 Run 전후 관찰·snapshot 이벤트와 주요 원본 SHA-256을 담는다. report의 bundle 경로만 저장소 상대 경로로 정규화했고 원래 보고서 경로와 SHA-256을 함께 보존했다. 통과한 정상 세 실행만 선별한 보고서가 아니다. 모든 case의 summary를 재계산했으며 normal/profile 29,000/s만 각각 3회 qualified=true다. 생성기 누락이 있는 다섯 실행은 완료 표식이 없으며 unsealed로도 탈락한다.

전체 바이너리·설정·서버 계측·계획/표본·run/WAL/snapshot·profile은 Git 제외 경로 `var/p6-baseline-4gm7mz4t/`에 보존했다. `trials.json`이 실행 목록, 각 `reports/NAME.json`은 개별 판정, `baseline-report.json`은 모든 실행의 재검증이다. parent의 분석 파일은 완료 묶음 밖에 두어 원본 해시를 변경하지 않았다. 큰 raw 묶음은 Git에 포함되지 않으므로 저장소 clone만으로 기존 실행의 표본을 얻을 수는 없다.

재현은 [고정 기준 판정](../development.md#고정-기준-판정)의 명령을 따른다. workload-v1.json의 requestsPerSecond만 29,000으로 바꾸고 normal/profile/snapshot을 각 3회 새 output에서 실행한다. 상단 실패점 30,000과 기존의 모든 실패 실행을 보고서 입력에서 제외하지 않는다. 원래 기준 바이너리는 각 묶음의 bin/에 있으며 다른 소스를 빌드한 뒤에는 그 복사본과 구분한다. profile 해석은 `scripts/go tool pprof -top -sample_index=cpu <묶음>/bin/exchange <묶음>/profiles/cpu.pprof`이고, capture 진단에는 `-focus='engine.*Capture' -cum`을 추가했다. heap은 inuse_space, allocs는 alloc_space로 읽었다.

P7은 같은 금액·순서·중복·내구성 계약, 입력·기간·판정 기준을 유지하고 개선 하나를 검증한 뒤 비교한다. 정상 조건의 회귀 여부와 snapshot 지연/누락 개선을 따로 확인한다. 이 보고서는 P7 변경 전 결과이며 snapshot을 켠 조건에서 채택 가능한 최대 처리량은 미확정이다. 후속 구현과 비교는 [P7 정렬 이동](p7-snapshot-sorting.md)에 기록한다.

결과는 20초 창에서 관찰한 지속 처리량이며, 영구히 이력을 유지하는 시스템의 무한 시간 처리량으로 일반화하지 않는다. 1,000/s 사이의 미측정 rate나 다른 호스트/시드/계정 집중도에 대한 전역 최대값도 주장하지 않는다. 실제 전원 장애는 별도 장비가 없어 미완료이며 부하 실험이나 프로세스 kill로 대체하지 않는다.
