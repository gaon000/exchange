# 지연 구간 분석과 생성기 진단

2026-11-02, [최적화 버전 10분 결과](optimized-soak-10m-comparison.md)의 현재 끔/켬 원본을 재분석했다. **지연 양상이 서로 다르다. 끔 조건의 500~515초에는 서버 WAL sync 지연이 함께 커졌고, 켬의 미전송 두 구간에는 생성기 전송 경로 지연도 있다. 단일 원인은 확정하지 않았다.** 이번 작업은 기존 기록 분석과 다음 실험을 위한 계측 추가이며 새로운 10분 실행이나 성능 개선 결과가 아니다.

[기계 판독 근거](20261102-latency-diagnostics.json)에 입력 해시, 선택 구간, 전체 단계 차분과 미전송 9건을 보존했다. 새 분석 원본은 Git 제외 `var/latency-diagnostics-20261102`에 있다. 기존 측정 파일은 변경하지 않았다.

## 관찰 결과

시간은 본 측정 시작 기준 초, 지연은 ms다. 요청 p99와 전송 완료 p99는 실제 클라이언트 표본의 nearest-rank 값이다. WAL sync 건수는 해당 시각 전 가장 가까운 두 서버 계측 사이 완료 표본의 histogram 차분이다. 서로 같은 요청 집합이 아니므로 건수를 일대일 대응하거나 단계 시간을 더하지 않는다.

| 조건·구간 | 요청 p99 | 생성기 예정→시작 최대 | 시작→전송 완료 p99 | 서버 WAL sync 20ms 초과 |
| --- | ---: | ---: | ---: | ---: |
| 끔 500~505초 | 39.280 | 1.686 | 0.172 | 9 |
| 끔 505~510초 | 35.183 | 2.422 | 0.186 | 14 |
| 끔 510~515초 | 24.883 | 4.405 | 0.314 | 1 |
| 켬 285~290초 | 204.657 | 76.103 | 93.258 | 1 |
| 켬 390~395초 | 48.413 | 85.041 | 4.948 | 0 |

켬의 예정→시작 열은 미전송의 경우 예정→거절 관찰 시간을 포함한다. 전송 완료는 HTTP transport의 WroteRequest callback 관찰이며 실제 NIC 전송 시간이나 서버 처리 시작 시간이 아니다.

### 스냅샷 끔의 500~515초

전체 관측 구간의 WAL sync 20ms 초과 27건 중 24건이 이 세 구간에 있다. 생성기 발사·전송 완료 지연은 상대적으로 작고, 서버 handler의 20ms 초과도 같은 구간에서 증가했다. 따라서 이 사례는 서버 저장 경로를 다음 진단 대상으로 좁힐 근거가 된다. sync 벽시계 시간에는 OS 스케줄링 지연도 포함되므로 SSD 자체의 원인으로 단정하지 않는다.

서버 GC는 첫 5초에 1회, 나머지 10초에는 0회였다. 관측된 GC pause의 가장 큰 bucket 상한은 0.229ms다. 이 관찰만으로 수십 ms 지연을 서버의 긴 GC pause로 설명할 수 없다. 호스트 자원 경쟁이나 생성기 GC는 구간별 기록이 없어 배제할 수 없다.

### 스냅샷 켬의 미전송 9건

- 약 288.01초부터 4건: 미전송 관찰 시각을 포함한 약 486ms 서버 계측 구간에는 GC 증가와 snapshot capture/publish 완료가 없었다. snapshot 호출도 관찰 시각에는 진행 중이 아니었다. 서버 대기열·batch·sync·handler 지연이 함께 보이고, 285~290초의 클라이언트 전송 완료 p99도 93.258ms였다. 단순한 snapshot 완료 비용만으로 설명하기 어렵다.
- 약 394.70초부터 5건: 약 500ms 서버 계측 구간에 snapshot capture 1회(48.806ms), GC 1회와 GC CPU 57.606ms가 기록됐다. GC pause bucket 상한은 0.131ms이며 WAL sync 20ms 초과는 없었다. snapshot 호출과 미전송이 겹치지만 생성기 실행 지연의 원인이라는 증거는 아직 없다.

누적 CPU 시간은 여러 스레드의 합이며 GC CPU와 pause는 다른 지표다. 표본의 현재 큐 길이가 0이어도 그 사이 요청이 기다리지 않았다는 뜻은 아니다. 기존 원본으로 미전송이 scheduler 검사에서 발생했는지 worker 검사에서 발생했는지는 구분할 수 없다.

## 시간 정렬과 분석 한계

클라이언트 표본은 monotonic offset, 서버와 snapshot 로그는 UTC다. `scheduleEpoch + offset`으로 대조했지만 실행 종료에서 UTC 경과 시간과 monotonic 경과 시간의 차이는 끔 약 -9.724ms, 켬 +1.483ms였다. 이 끝점 차이가 실행 중 모든 시점의 오차 상한이라는 뜻은 아니다. 서버도 여러 지표를 동시에 고정하지 않는다.

서버 표본은 약 500ms 간격이다. 선택한 5초 구간의 경계는 실제 클라이언트 경계보다 끔 약 246ms, 켬 약 133ms 앞에 있는 서버 관찰을 사용한다. 짧은 지연의 정확한 시작·끝이나 같은 명령의 단계별 인과관계를 복원할 수 없다. 전체 단계 차분에서도 capture 120개와 publish 119개처럼 완료 분모가 다르다.

분석 입력 9개 파일의 SHA-256을 기존 manifest와 대조했다. 현재 두 실행의 5초 구간 240개에 대해 요청 p99·최대·예정·미전송 수를 기존 Go 재집계와 대조했고, 단계별 histogram 차분 합계가 전체 차분과 일치했다. 데이터의 새 성능 합격 판정이나 이전 실패의 제외는 하지 않았다.

재현 명령은 저장소 루트에서 `python3 var/latency-diagnostics-20261102/analyze.py`, 이어서 `python3 var/latency-diagnostics-20261102/verify_report.py`다. 기존 출력이 있으면 bytes 일치를 검사하며 덮어쓰지 않는다. 전체 분석과 분석 스크립트 SHA-256은 기계 판독 근거에, 검증 스크립트와 최종 산출물 해시는 로컬 `artifact-manifest.json`에 기록한다.

## 추가한 선택적 진단

`loadgen`과 `experiment`에 `--diagnostics-interval 500ms`를 추가했다. 기본값 0은 비활성이며 100ms~1m를 허용한다. 기존 workload 파일·입력 digest·요청 deadline·설정된 lateness 한도·누락 판정은 그대로 적용된다. 자세한 필드 의미와 검증은 [측정 계약](../design-docs/benchmark-v1.md#생성기-진단-옵션)에 있다.

| 산출물 | 추가 관찰 |
| --- | --- |
| dispatch.jsonl | 모든 예정 인덱스의 scheduler 전달 전 관찰과 worker 첫 실행 시각. 미전송에서도 관찰한 경계는 유지 |
| generator-metrics.jsonl | 생성기 CPU·GC·heap·goroutine의 initial/periodic/final, 실제 수집 시각과 건너뛴 주기 |
| manifest.json / run.json | 선택한 주기, 수집 기준 UTC, 기록 수·상한 도달 여부와 dispatch 활성 여부 |

진단 수집은 메모리에 보존하고 Run 종료·worker 합류 후 파일을 쓴다. 추가 메모리는 입력 건수(기존 최대 200만)에 비례한 dispatch 배열과 최대 40,000개의 주기 자원 표본, initial/final로 제한한다. 수집이 늦으면 건너뛴 주기를 기록하고 과거 시각의 표본을 만들어 채우지 않는다. 한도에 도달하면 부분 기록과 final을 남기고 실행을 실패 처리한다. 종료·취소에서도 collector에 합류한다.

기본 실행은 기존 여섯 원본만 남는다. 진단 실행은 추가 두 파일까지 여덟 파일의 해시를 기록한다. 실험 실행기는 진단 설정·실행 경계·완전한 수집 순서·건수·해시를 확인한다. 실제 원본 표본 형식과 거래 API/WAL/snapshot 형식은 변경하지 않았다.

`benchreport`는 추가 파일의 해시와 기존 요청 통계를 재검증하고 진단 주기별로 비교 series를 분리한다. 기존 무진단 기준에는 `GENERATOR_DIAGNOSTICS_ENABLED`를 남겨 합격/최대 처리량으로 채택하지 않는다. 진단 스트림의 의미 검사는 experiment가 담당하며 benchreport의 요청 재집계를 해당 검사로 대신하지 않는다.

계측에도 CPU·할당·메모리 비용이 있다. 이번에는 그 비용을 수치화하지 않았다. 다음 비교는 끔/켬 양쪽에서 같은 진단 설정을 사용하며 기존 무진단 실행과 직접적인 성능 개선율을 주장하지 않는다. 진단은 지연이 관찰된 경계를 좁히고, 필요하면 별도의 trace 실험으로 원인을 확인하기 위한 자료다. 전체 호스트 CPU·I/O·다른 프로세스의 상태까지 수집한 것은 아니다.

## 검증과 다음 단계

관련 race 테스트에서 기본 비활성, scheduler 지연, worker 경계의 잘못된 관찰 거절, 포화·취소, sampler 지연·한도, 부분 파일 보존을 검사했다. 실제 HTTP/APFS 실험에서 진단을 켠 정상·snapshot/profile 실행과 원본 잘림·중복 검출을 확인했다. 최종 portable 200개·native race 232개 테스트와 포맷·vet·build를 통과했다. 전체 검증 결과는 [완료 계획](../exec-plans/completed/20261102-latency-diagnostics.md)에 기록한다.

후속 작업은 동일 진단 설정으로 끔/켬 순서를 교대해 각각 10분 3회 측정하고 재현 여부를 확인하는 것이다. 이번에는 실행하지 않았다. 특정 엔진 최적화나 OS 설정 변경도 수행하지 않았다. 실제 전원 장애 검증은 계속 보류다.
