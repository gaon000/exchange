# exchange 제품 명세

상태: Accepted
합의 반영일: 2026-10-29 (Asia/Seoul)
구현 상태: P4까지 도메인·엔진·Genesis/WAL·단일 소유자 runtime·snapshot 생성 및 재시작 복구 완료. P5 HTTP 계층·초기화/실행 CLI와 실제 거래·과부하·저장 오류·종료·재시작 검증을 추가했다. P6의 [기준 측정](../benchmarks/p6-baseline.md)은 완료했으며 P7 개선·최종 비교와 실제 전원 장애 검증은 남아 있다.

## 목적과 사용자

개발자가 주문 처리·영구 저장·복구 경로를 구현하며 학습하고, 성능 개선의 근거를 포트폴리오로 제시한다. 사용자는 개발자와 테스트 계정이며 실제 자산을 취급하지 않는다.

사용자가 단계별 질문에서 선택한 범위와 상세 설계의 문서 반영 요청을 근거로 작성했다. Accepted는 범위·동작의 합의이며 구현이나 성능·장애 검증의 증거가 아니다.

## 첫 버전 범위

| 항목 | 합의 |
| --- | --- |
| 거래 대상 | 가상자산 현물 모의 거래, 단일 거래쌍 |
| 결과물 | 거래 API, 부하 생성기, 재현 가능한 성능 보고서 |
| 기준 환경 | 현재 개발용 컴퓨터 한 대 |
| 주문 | 지정가, 부분 체결, 미체결 잔량 취소 |
| 거래 상대 | 별도의 테스트 계정이 제출한 주문 |
| 자금 | 새 실험 준비 시 초기 잔고 설정, 일반 재시작 시 기존 상태 복구 |
| 성능 목표 | p99 응답 시간 상한을 지키는 최대 지속 처리량 |
| 복구 목표 | 저장장치가 정상인 조건에서 성공 응답한 변경을 OS 종료·전원 장애 후 복구 |

## 사용자 행동

1. 초기 계정·잔고·실험 설정을 준비한다.
2. 지정가 주문을 제출하고 호가창 등록 또는 체결 결과를 받는다.
3. 주문·호가창·잔고·체결 내역을 조회한다.
4. 활성 주문의 남은 수량을 취소한다.
5. 응답을 못 받으면 같은 ID와 내용으로 재시도해 최초 결과를 확인한다.
6. 서버를 재시작하고 기존 상태와 처리 결과를 복구한다.
7. 같은 실험 조건의 부하를 반복하여 처리량·지연·거절·복구 결과를 비교한다.

## 제품 정책과 예외

| ID | 규칙 |
| --- | --- |
| EX-R01 | 매수는 가장 낮은 매도 가격, 매도는 가장 높은 매수 가격부터 체결한다. 같은 가격은 서버 주문 순번이 앞선 주문을 우선한다. |
| EX-R02 | 실제 체결 가격은 먼저 호가창에서 기다리던 주문의 가격이다. |
| EX-R03 | 일부 체결은 유지하고 미체결 잔량만 취소할 수 있다. 미체결 주문은 취소될 때까지 대기하며 v1에는 수정·자동 만료가 없다. |
| EX-R04 | 자기 거래를 차단한다. 같은 계정의 상대 주문을 만나면 새 주문의 잔량을 취소하고, 기존 주문과 이미 다른 계정과 체결한 부분은 유지한다. |
| EX-R05 | 새 주문의 최대 필요 금액·수량을 전부 예약한다. 부족하면 전체 주문을 거절한다. 가격 개선 차액과 취소 잔량의 예약분은 반환한다. |
| EX-R06 | 수수료는 없다. 거래·예약·해제 과정에서 자산별 전체 공급량이 보존되어야 한다. |
| EX-R07 | 주문 처리와 복구 가능한 영구 기록이 끝난 뒤 결과를 응답한다. 주문 접수와 주문 승인은 구분한다. |
| EX-R08 | 대기열이 가득 차면 이번 시도를 접수하지 않고 즉시 거절한다. 같은 ID로 시도했던 과거 요청의 미처리까지 보장하는 응답은 아니다. |
| EX-R09 | 같은 실험·계정·명령 종류·요청 ID와 같은 내용의 재시도는 한 번만 실행하고 최초 결과를 반환한다. 같은 키의 다른 내용은 충돌로 거절한다. |
| EX-R10 | 잔고 부족 등 최종 거절 결과도 재시도 시 유지한다. 다시 주문하려면 새 ID를 사용한다. 취소에도 별도 요청 ID를 사용한다. |
| EX-R11 | 연결 종료·타임아웃은 이미 접수한 주문을 자동 취소하지 않는다. 결과가 불확실하면 같은 ID로 재시도한다. |
| EX-R12 | 초기 잔고는 새 실험을 준비할 때만 설정한다. 일반 재시작은 기존 상태를 복구하며 초기 잔고를 다시 지급하지 않는다. |
| EX-R13 | 실험 중 중복 처리 기록을 만료시키거나 요청 ID를 재사용하지 않는다. 최초 응답과 현재 주문 상태는 별도이며 현재 상태는 조회 API로 확인한다. |

주문 상태·잔고 계산식·명령 순번과 복구 알고리즘은 [상세 설계](../design-docs/exchange-v1.md)가 소유한다.

## 성능 결과의 판정

- 응답 시간 상한은 p99 기준이며 모든 요청의 절대 최대 지연을 보장한다는 의미가 아니다.
- 요청 접수부터 영구 저장·상태 적용·응답까지의 전체 경로를 측정한다. 클라이언트의 예정 발사 시각과 실제 전송 지연도 기록한다.
- 새로운 유효 주문의 성공 처리량, 취소 처리량, 체결 수, 업무 거절, 과부하 거절, 중복 응답, 타임아웃을 분리한다.
- 즉시 거절·중복 응답 수를 거래 처리량으로 합산해 성능을 높게 보고하지 않는다.
- p99 상한·허용 거절률·부하 비율·측정 기간은 초기 측정 후 비교 실험 전에 고정한다. 대기열이 계속 커지거나 시간이 지나며 성능이 무너지는 상태를 지속 처리량으로 보고하지 않는다.
- 로컬 서버와 부하 생성기가 같은 CPU·디스크를 공유한다는 한계, 프로파일러·스냅샷의 영향을 기록한다.

## 범위 밖

실제 자산·실입출금, 실행 중 모의 입출금, 수수료, 시장가·파생상품, 다중 거래쌍, 주문 수정·자동 만료, 웹 거래 화면, 분산 서비스·고가용성 복제, 운영 배포는 첫 버전에서 제외한다. 디스크 자체의 손상·유실을 복제 없이 복구하는 것은 목표가 아니다.
